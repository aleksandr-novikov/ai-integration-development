# ADR-001: сохранить Flask и выделить учебный инференс

Дата: 13.10.2026; уточнено 15.10.2026 по ревью Раиля. Статус: решение подготовлено для повторного командного ревью в задаче #3; FastAPI-слой ещё не реализован. База анализа: `59c54fa`.

## Контекст и требования

Flask уже объединяет страницы Jinja2, API, сессии Flask-Login, CSRF, управление проектами и подключениями. SQLAlchemy, сборщики и `ml/` содержат основную логику. Переписывание приложения потребует повторной проверки пользовательских сценариев и изоляции, не улучшая само по себе качество Isolation Forest.

Материалы курса проверены 13.10.2026:

- `В02_Архитектура_ИИ-систем_микросервисы_batch_stream.pdf`, слайд 51: компоненты, потоки, стек; формат около двух страниц. Конкретный веб-фреймворк этим заданием не предписан.
- `ПРЕЗЕНТАЦИЯ_ИТОГОВОГО_ПРОЕКТА.pdf`, слайды 7–8: архитектура, контракт при наличии сервиса, обоснование стека и описание запуска.
- Там же, слайд 10, строка В09–В12: прямо указан **FastAPI-сервис**. Поэтому считать Flask достаточным для всего курса без отдельного согласования нельзя.
- Презентации В09–В12 в доступной папке отсутствуют. Подробности уточняются в #22; это не отменяет уже известного требования итогового задания. Отдельного подтверждения преподавателем замены FastAPI на Flask у команды в этих материалах нет.

## Решение

Сохранить модульный Flask-монолит как UI и контур сбора/хранения. В #12 добавить небольшой FastAPI-сервис инференса с 1–2 согласованными в #4 эндпоинтами. Повторно использовать логику построения признаков и предсказания из `ml/` через явно выделенные функции. Не запускать в этом сервисе Flask-фабрику, APScheduler и обучение на запросе.

Целевая граница: запрос с валидированными признаками и проверенным контекстом → загрузка выбранной модели/scaler → предсказание → результат с идентификатором версии. Артефакт и схема признаков должны быть связаны с данными, кодом и MLflow-run в #5. Контракт #4 определит точные поля, авторизацию, ошибки отсутствующей модели и несовместимых признаков. Прямой импорт нынешнего `score_table` недостаточен: он читает историю из хранилища и может обучить модель.

### Рабочая модель и согласованность с дашбордом

Для нового контура источник истины — **явно опубликованная неизменяемая версия из MLflow**, выбранная после проверки качества. Активную версию задаёт манифест выпуска, а не последний изменённый `models/*.joblib` и не автоматически выбранный последний run. Манифест связывает `model_version`, `run_id`, git SHA, идентификатор данных, версию схемы признаков и контрольные суммы модели/scaler. Точный формат и загрузка skops/joblib определяются в #5; произвольная десериализация внешних артефактов не является контрактом.

После перехода ночное обучение создаёт **кандидатов**; оно не переключает активную модель и не перезаписывает опубликованные файлы. Публикация после проверки и откат на предыдущий манифест — явные операции (#5/#14). Текущая серия #9 с FPR 13,27% не получает положительного допуска: её можно закрепить только для явно обозначенной учебной демонстрации провала качества, а не представить как готовую рабочую модель. Новая серия и её допуск выполняются отдельно.

В #12 фоновый скоринг, питающий дашборд для переведённого учебного сценария, должен обращаться к тому же FastAPI-сервису и опубликованному артефакту. Сервис фиксирует модель/scaler на время запроса и возвращает фактически использованные `model_version` и `feature_schema_version`; эти идентификаторы сохраняются со scores (#5/#12). Дашборд показывает версию результата: старые scores не переименовываются при переключении модели, данные разных версий не смешиваются в одну оценку качества. Это позволяет сравнить один вход через API и в дашборде и проверить совпадение score и версии. Общая директория с перезаписываемыми файлами не обеспечивает такую согласованность.

**Обязательная миграция хранилища в #12 (идентификаторы из #5).** Сейчас первичный ключ `anomaly_scores` и конфликт upsert в `save_anomaly_scores` — `(project_id, ts, table_name)`, без версии. Например, `warmup_ml.py` пересчитывает последние 14 дней и при смене модели может затереть прежние результаты. Одного добавления версии в ответ API недостаточно.

Для нового контура выбрать хранение с версионным ключом: добавить обязательные `model_version` и `feature_schema_version` и включить оба поля в первичный/уникальный ключ и условие upsert вместе с проектом, идентичностью источника и временем. Для нынешней идентичности таблицы это `(project_id, ts, table_name, model_version, feature_schema_version)`; контракт #4 должен дополнить идентичность источника для одноимённых таблиц разных подключений до реализации миграции. Повторная запись того же входа с той же парой версий идемпотентна; другая версия создаёт отдельную запись. Чтение для дашборда и оценки качества явно выбирает пару версий и возвращает её, без неявного объединения разных моделей.

Существующие строки сохранить с зарезервированными маркерами `legacy-unknown` в обоих полях: их происхождение неизвестно, приписывать им активную или предполагаемую историческую модель нельзя. Маркеры не допускаются для новых опубликованных версий; старые строки показываются отдельно. Миграция сохраняет оставшиеся данные, но не восстанавливает уже перезаписанную историю. Переключение и откат активного манифеста не удаляют scores других версий.

Критерии приёмки #12: миграция существующей SQLite/PostgreSQL базы без потери строк; пересчёт одного timestamp двумя версиями сохраняет оба результата; повтор той же версии не создаёт дубль; смена схемы признаков также сохраняет отдельный результат; выбор версии в API/дашборде и откат не смешивают и не стирают историю. Проверки должны учитывать согласованную в #4 идентичность источника. Эти изменения схемы, записи и чтения — обязательная часть перехода в #12, **не реализация в этом документационном PR**.

**До миграции** планировщик продолжает обновлять legacy joblib, а дашборд читает прежние scores. Их равенство с экспериментальным FastAPI пока не обещается. Параллельная демонстрация должна явно обозначать старый и новый контуры; полное переключение входит в #12, а не в этот PR.

### Кто рассчитывает признаки

Историю читает **вызывающая сторона в Flask-контуре**: адаптер между сбором/хранилищем и новым inference API. Она определяет разрешённый проект и источник, получает совпавшие по времени `row_count` и `null_rate`, выбирает текущее и предыдущее наблюдения. Изолированный FastAPI-сервис не подключается к хранилищу метрик и не держит собственную историю.

Расчёт выполняет одна чистая функция в общем модуле `ml/`, используемая и обучением, и вызывающим адаптером (#5/#12): `[row_count, null_rate, row_count - previous_row_count, null_rate - previous_null_rate]`. Порядок, типы и правила пропусков входят в версию схемы признаков. Сохраняется текущая семантика `_load_features`: предыдущая точка — предыдущее доступное согласованное наблюдение, разности не нормируются на длительность разрыва. Если пары нет, выдаётся состояние недостаточной истории, без подстановки нулей и без обучения. Идентичность источника при одинаковых именах таблиц должна быть определена контрактом #4 до реализации; произвольного `project_id` от клиента недостаточно для авторизации.

FastAPI получает четыре **немасштабированных** признака, версию их схемы и проверенный контекст. Он валидирует формат, конечность и совместимость со схемой, применяет scaler выбранного артефакта и вычисляет предсказание. Дельты повторно не вычисляются, scaler не обучается. Доступ к этому внутреннему контракту предназначен авторизованному адаптеру; валидный JSON сам по себе не доказывает происхождение признаков. Способ сервисной аутентификации, точные поля и коды ошибок фиксируются в #4.

Приёмочные сценарии для #4/#5/#12: одинаковые признаки в offline-обучении и online-адаптере; пропущенная предыдущая точка и несовпавшие timestamps; отсутствие/несовместимость артефакта без скрытого fit; смена и откат версии с сохранением правильной версии каждого score; совпадение API и дашборда на одном входе. Реализация этих сценариев ещё предстоит.

Способ демонстрации фиксируется в #12/#13 после контракта. Существующие маршруты не удаляются и не переименовываются этой документационной задачей. До реализации нельзя показывать FastAPI как работающий компонент текущей схемы.

## Альтернативы и последствия

| Вариант | Оценка |
|---|---|
| Только Flask | Меньше изменений, но остаётся несоответствие слайду 10; допустим только при фактическом согласовании исключения |
| Переписать всё на FastAPI | Большая миграция UI/сессий/прав и сборщиков без необходимости для выбранного ML-кейса |
| Flask + небольшой сервис инференса | Выполняет учебное требование с ограниченной новой границей; выбран для #12 |
| Разнести сбор, обучение, UI и уведомления по микросервисам | Пока нет подтверждённой потребности; усложняет развёртывание, доступ и диагностику |

Новый сервис потребует отдельной конфигурации, доставки артефактов, health/readiness, контрактных тестов и измерений latency. Общие Python-модули не должны порождать два несовместимых препроцессинга. Асинхронный HTTP сам по себе не ускоряет CPU-инференс и обучение; нагрузочные утверждения проверяются измерениями, а не выбором фреймворка.

Пересмотреть решение при уточнении лекций/ответе преподавателя либо измеренной необходимости независимого масштабирования. До этого текущий Flask-контур остаётся одним экземпляром с внутрипроцессным scheduler. Вынос фоновых заданий — отдельное изменение, не скрытая часть перехода к FastAPI.
