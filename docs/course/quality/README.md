# Качество модели — задача #10

**Программные проверки проходят, а текущая baseline не проходит критерий качества FPR.** Это разные результаты: pytest проверяет корректность поведения и оценки, отдельная команда качества запрещает считать модель готовой при нарушении целей CASE.md. Порог модели и результаты серии #9 не изменены.

## Повторить

Из корня репозитория после установки `requirements-dev.txt`:

```bash
python -m pytest tests/test_model_quality.py tests/test_quality_report.py tests/test_anomaly_detector.py tests/test_anomaly_alert_quality.py -q
python -m scripts.check_model_quality --report /tmp/model-quality.json
```

Первая команда должна завершиться кодом 0. Для сохранённой baseline вторая команда должна завершиться **кодом 1 (FAIL)** и записать отчёт. Код 0 означает выполнение всех целей, код 2 — повреждённый вход или неверные аргументы. В процедуре допуска модели использовать именно код завершения команды качества; один только зелёный pytest не является допуском модели. Автоматический выпуск модели этим PR не настраивается.

## Поведенческие тесты

Тесты используют рабочие `ml.anomaly_detector.train()` и `score_table()`; подменяется только чтение метрик из БД. Реальные Isolation Forest, StandardScaler и сохранение/загрузка joblib остаются в проверке. Модель обучается на 640 исходных наблюдениях февраля (639 признаковых строк) с seed данных 103. Проверочные окна марта имеют другой seed 211 и не пересекаются с train. Во время scoring вызов train заменён запретом: незаметное дообучение приводит к ошибке теста.

| Проверка | Ожидаемое поведение |
|---|---|
| Пустая история, 1 и 200 исходных точек | InsufficientDataError, артефакт модели не создаётся; после удаления первой точки остаётся меньше MIN_POINTS=200 |
| Независимый стабильный ряд | 256 предсказаний, конечные score, доля ложных сигналов ≤10% |
| Всплеск NULL | Сигнал внутри известного интервала |
| Скачок объёма | Сигнал внутри известного интервала |
| Смена режима | Сигнал внутри известного интервала |
| Повышенный шум измерения | Конечные score; больше ложных сигналов, чем на стабильном ряду |
| Пропуски трёх измерений null_rate | Только совпавшие временные точки, без заполнения нулями; дельта пересчитывается от предыдущего доступного наблюдения |
| Повторный scoring | Полное совпадение результата без переобучения |

Это 10 pytest-случаев с параметризацией. Они расширяют поведенческое покрытие существующего `tests/test_anomaly_detector.py`, который также запускается. Отдельные синтетические сценарии проверяют ожидаемое поведение, а не доказывают общее качество на реальных данных. В сценариях baseline стационарна, поэтому их успешный результат не опровергает высокий FPR на растущих таблицах набора #9.

Ещё 12 случаев проверяют границы критериев, отказ при отсутствии/NaN/inf метрик, корректное отклонение сохранённой baseline, сохранение знаменателей при разбиении, защиту от изменения метрик/разметки/решений в архиве, код завершения CLI и защиту исходного архива от перезаписи. Унаследованные тесты фильтров уведомлений учитываются отдельно от качества сырых ML-сигналов.

## Оценка неизменного результата #9

`check_model_quality` читает сохранённые предсказания `final_test` из [архива MLflow](../experiments/mlflow-export.zip). Модель не загружается, не обучается и не выбирается повторно. Для проверки происхождения данных генератор воспроизводит исходные CSV и интервалы по манифесту: проверяются SHA-256, совпадение признаков/времени/разметки с входом сохранённых предсказаний. Пересчитанные общие метрики и результаты событий должны совпасть с записанными в MLflow.

Это аудит уже раскрытого test, **не новая независимая оценка и не новый эксперимент**. Для следующего подбора понадобится отдельно запланированная серия и новый закрытый тестовый период. Команда использует текущий генератор; при его несовместимом изменении нужно восстановить исходную версию, а не заменять хеши архива.

Полные метрики находятся в JSON-отчёте.

## Пороги, стоимость ошибок и принятые ограничения

Пороги взяты из CASE.md до оценки: event recall ≥80%, FPR ≤10%, медиана задержки резких событий ≤1 тик. При девяти событиях требуется найти хотя бы восемь. Один тик — 15 минут. Порог решения модели остаётся `decision_function < 0`, contamination=0.01 выбран в #9 на validation.

240 ложных сигналов за недельный тестовый период — около 34 сырых сигналов в день на три таблицы. Это расход внимания при проверке данных; число не равно числу Telegram-уведомлений, поскольку в продукте есть дополнительные фильтры. Лимит 10% допускает не более 180 ложных сигналов на этих 1809 нормальных точках; фактический результат выше на 60 сигналов. Пропуск инцидента означает задержку расследования, поэтому ограничение на FPR не заменяет event recall.

Общая медиана задержки равна 0, но скачки объёма users и orders обнаружены через 5 и 2 тика (75 и 30 минут). На срезе volume_jump медиана 2 тика. Это диагностическая слабость, которую скрывает общая медиана; новый обязательный порог по срезу задним числом не вводится.

Принятое ограничение: baseline остаётся учебным результатом и **не получает положительный допуск по качеству**. Не подбираем параметры по раскрытому test, не повышаем предел FPR и не скрываем результат через xfail/skip. Следующая серия должна исследовать ложные сигналы на train/validation, устойчивые к росту признаки и задержку объёмных инцидентов с отдельным закрытым test. Поведение при пропусках также требует внимания: дельта между доступными точками не нормируется на длительность разрыва; строгий CSV-валидатор #8 такие разрывы отклоняет, а эксплуатационный детектор использует совпавшие наблюдения.
