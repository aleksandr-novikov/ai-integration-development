# Дрейф данных и проверяемое переобучение

DB Monitoring · ДЗ В13 / #17 · 25.10.2026

## 1. Объект и границы

Isolation Forest выявляет аномалии по четырём признакам: `row_count`, средней по колонкам `null_rate` и их разностям `d_row_count`, `d_null_rate` между согласованными наблюдениями. Дрейф данных означает изменение распределений этих входов; дрейф концепта — изменение связи входов с подтверждёнными инцидентами. Изменение схемы БД (schema drift) проверяется отдельно: это повод проверить совместимость, а не автоматически обучать модель.

Предлагаемая ниже политика относится к одному источнику `(project_id, connection_id, schema_name, table_name)` и одной версии признаков. Историю с недоказанным источником не смешиваем. Сейчас код различает проект и имя таблицы, но этого недостаточно для одноимённых таблиц разных подключений; полная идентичность и её миграция остаются в #12. Пороги ниже — начальные инженерные настройки, их эффективность на реальном потоке ещё не измерена.

## 2. Признаки, эталон и обнаружение

Эталон — зафиксированные 14 суток проверенных нормальных данных, соответствующие обучению выбранной модели: UTC, шаг 15 минут, до 1344 согласованных векторов. Эталон хранится с хешем данных и версиями модели/признаков; после сигнала автоматически не обновляется. Текущее окно — последние завершённые 72 часа (до 288 векторов); окна для подтверждения сигнала не перекрываются. В каждом окне и эталоне нужны минимум 200 валидных векторов и покрытие не менее 90% ожидаемых точек. Иначе статус `insufficient_data`, восстановление сбора, без вывода «дрейфа нет» и без переобучения. Плановое расписание сбора определяет ожидаемое число точек.

Для каждого из четырёх числовых признаков считаем KS-расстояние D между выборками. Сигнал: **D ≥ 0,10 и p < 0,0125** (0,05 / 4, поправка на четыре сравнения). Для объяснения считаем PSI по фиксированным децильным границам эталона с крайними интервалами до ±∞; повторяющиеся границы объединяем. **PSI > 0,20 — предупреждение; > 0,25 — сильный сдвиг**. Бины текущего окна не подгоняем. Срабатывание любого метода открывает расследование; два последовательных неперекрывающихся окна с сигналом по одному признаку дают устойчивый сигнал. Для постоянного признака вместо вырожденных децилей используются три бина: ниже, равно, выше значения эталона.

Отдельно наблюдаем пропуски, свежесть, нарушения диапазонов и долю аномальных scores (#16). NULL не заменяем нулём; отрицательный `row_count`, `null_rate` вне [0,1], разрыв сбора или несовместимая схема сначала требуют исправления данных. `score < 0` — порог аномалии, не порог дрейфа. PSI/KS не доказывают падение качества или дрейф концепта. Из-за автокорреляции временных рядов p является эвристикой: учитываем D, сезонность и подтверждение оператором; валидация политики требует отдельных нормальных периодов и блочного анализа ложных сигналов. Задержка подтверждения может достигать шести суток, поэтому острые инциденты продолжают обрабатываться обычными алертами.

## 3. Решение и данные для переобучения

Выбираем **переобучение по событию с ручным допуском**. После устойчивого сигнала ответственный за ML проверяет сбор, изменения бизнеса и подтверждения владельца данных. При сбое исправляем сбор; при разовом инциденте исключаем его из нормального обучения; при подтверждённом устойчивом нормальном режиме готовим кандидата. При изменении смысла инцидента сначала получаем новую разметку. Непрерывное обучение не выбираем из-за риска усвоить инциденты как норму. Еженедельный просмотр отчёта служит страховкой, но не запускает автоматическую замену модели.

Берём до 60 последних суток с доказанной идентичностью источника, убираем подтверждённые инциденты и сбои сбора, сохраняем нормальные сезонные режимы. Нужно минимум 200 векторов и покрытие требуемых режимов; 200 точек само по себе не доказывает репрезентативность. Владелец данных подтверждает норму/инцидент по журналу изменений и расследованиям. Решение самой модели не является истинной меткой. Без такой обратной связи допускается исследовательский кандидат, но не заявление об улучшении precision/recall/FPR или автоматический выпуск.

## 4. Проверка кандидата, выпуск и откат

До обучения фиксируем хеши снимков, UTC-границы train/validation/нового test, seed, код и правила выбора. Scaler обучаем только на train. Кандидат и действующая модель проверяются на одинаковом независимом будущем периоде; параметры выбираем только на validation. Уже раскрытый test серии #9 остаётся регрессией, а не новым независимым доказательством. При недостатке подтверждённых событий выпуск ждёт данных. Требования: event recall ≥80%, FPR ≤10%, медиана задержки резких событий ≤1 тик; дополнительно показываем числа событий, TP/FP/FN/TN, результаты по таблицам, худшие задержки и неопределённость на малой выборке. Кандидат не должен ухудшать эти три метрики относительно действующей модели; при компромиссе — новый заранее согласованный протокол, без подгонки после test.

После проверки второй участник команды подтверждает отчёт и точный ID связки model/scaler; сохраняются старый ID, схема, эталон и результаты. Переключение выполняется явно, без fit при инференсе. На первом полном 72-часовом окне контролируем ошибки, свежесть и сигналы; при невозможности загрузки/несовместимости откатываем сразу, при подтверждённом нарушении критериев качества — после разбора. Откат выбирает прежний проверенный ID и его эталон, без переобучения. Если допущенной прежней модели нет, ML-выпуск блокируется; остаются явно обозначенная учебная демонстрация и правила мониторинга.

Текущая baseline #9 имеет FPR **13,27%**: она не допущена и не считается безопасной точкой отката. Legacy scheduler сейчас обучает IF ежедневно в 04:00 по часовому поясу процесса и перезаписывает joblib без этой процедуры. Подключение безопасного выпуска к scheduler/API — #12; метрики и уведомления — #16. #17 поставляет стратегию и проверяемый учебный сценарий, не выдаёт их за работающую автоматизацию.
