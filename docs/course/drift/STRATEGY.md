# Дрейф данных и проверяемое переобучение

DB Monitoring · ДЗ В13 / #17 · 25.10.2026, ред. 08.11.2026

## 1. Объект и границы

Isolation Forest выявляет аномалии по четырём признакам: `row_count`, средней по колонкам `null_rate` и их разностям `d_row_count`, `d_null_rate` между согласованными наблюдениями. Дрейф данных означает изменение распределений этих входов; дрейф концепта — изменение связи входов с подтверждёнными инцидентами. Изменение схемы БД (schema drift) проверяется отдельно: это повод проверить совместимость, а не автоматически обучать модель.

Предлагаемая ниже политика относится к одному источнику `(project_id, connection_id, schema_name, table_name)` и одной версии признаков. Историю с недоказанным источником не смешиваем. Текущий расчёт дрейфа объединяет одноимённые таблицы разных подключений; разделение — в #16. Пороги ниже — начальные инженерные настройки, их эффективность на реальном потоке ещё не измерена.

## 2. Признаки, эталон и обнаружение

Эталон — зафиксированные 14 суток проверенных нормальных данных, соответствующие обучению выбранной модели: UTC, шаг 15 минут, до 1344 согласованных векторов. Эталон хранится с хешем данных и версиями модели/признаков и после сигнала сам не обновляется. Текущее окно — последние завершённые 72 часа (до 288 векторов); окна для подтверждения сигнала не перекрываются. Вектор валиден, если все четыре значения конечны (без NaN/±Inf) и в физических границах: `row_count` ≥ 0, `null_rate` в [0,1]. Разность через пропуск сбора не нормируется, а исключается. В эталоне и окне после проверки нужны ≥200 валидных векторов и покрытие ≥90% точек расписания. Иначе `insufficient_data`; если объёма хватает, но есть невалидный вектор, — `invalid_data`. Оба статуса ведут к исправлению сбора, без вывода «дрейфа нет» и без переобучения.

Для `null_rate`, `d_row_count`, `d_null_rate` считаем KS-расстояние D между выборками. Сигнал: **D ≥ 0,10 и p < 0,0125** (0,05 / 4, поправка на четыре проверки). PSI для объяснения считаем по фиксированным децилям эталона с крайними интервалами до ±∞ (повторы границ объединяем). **PSI > 0,20 — предупреждение; > 0,25 — сильный сдвиг**. Бины текущего окна не подгоняем. Постоянный признак делим на три бина: ниже, равно, выше эталона.

Растущий при обычном накоплении `row_count` против фиксированного эталона даёт KS/PSI-сигнал в каждом окне, поэтому для уровня они только описательные. Норму роста задаёт `d_row_count`: сигнал по нему — изменение темпа вставок или удалений. Уровень сверяем с трендом эталона: через n шагов после конца эталона ожидаем последнее значение эталона + μn с допуском **±4σ√n** (μ, σ — среднее и SD `d_row_count` эталона). **≥10% точек окна вне коридора** — сигнал `row_count` (скачок уровня). Дальше длины эталона тренд не продлеваем: `baseline_expired`, пересмотр эталона. Если ≥10% точек лишь вне диапазона эталона, а приращения и коридор в норме, — `expected_growth`: не дрейф, а выход входа IF за диапазон обучения (раздел 3). Любой сигнал открывает расследование; два последовательных окна с сигналом по одному признаку — устойчивый сигнал.

Отдельно наблюдаем свежесть и долю аномальных scores (#16); NULL не заменяем нулём, несовместимую схему сначала исправляем. `score < 0` — порог аномалии, не порог дрейфа. PSI/KS не доказывают падение качества или дрейф концепта. Из-за автокорреляции p — эвристика: учитываем D, сезонность и подтверждение оператора; валидация политики требует отдельных нормальных периодов и блочного анализа ложных сигналов. Два полных окна — шесть суток, при частично затронутом первом окне дольше; острые инциденты ловят обычные алерты.

## 3. Решение и данные для переобучения

Выбираем **переобучение по событию с ручным допуском**. После устойчивого сигнала ответственный за ML проверяет сбор, изменения бизнеса и подтверждения владельца данных. При сбое исправляем сбор; при разовом инциденте исключаем его из нормального обучения; при подтверждённом устойчивом нормальном режиме готовим кандидата. Два окна `expected_growth` подряд — плановое событие: владелец подтверждает рост как норму, и кандидат обучается на свежих данных. При изменении смысла инцидента сначала получаем новую разметку. Непрерывное обучение не выбираем из-за риска усвоить инциденты как норму. Еженедельный просмотр отчёта служит страховкой, но не запускает автоматическую замену модели.

Берём до 60 последних суток с доказанной идентичностью источника, убираем подтверждённые инциденты и сбои сбора, сохраняем нормальные сезонные режимы. Нужно минимум 200 векторов и покрытие требуемых режимов; 200 точек само по себе не доказывает репрезентативность. Владелец данных подтверждает норму/инцидент по журналу изменений и расследованиям. Решение самой модели не является истинной меткой. Без такой обратной связи допускается исследовательский кандидат, но не заявление об улучшении precision/recall/FPR или автоматический выпуск.

## 4. Проверка кандидата, выпуск и откат

До обучения фиксируем хеши снимков, UTC-границы train/validation/нового test, seed, код и правила выбора. Scaler обучаем только на train. Кандидат и действующая модель проверяются на одинаковом независимом будущем периоде; параметры выбираем только на validation. Уже раскрытый test серии #9 остаётся регрессией, а не новым независимым доказательством. При недостатке подтверждённых событий выпуск ждёт данных. Требования: event recall ≥80%, FPR ≤10%, медиана задержки резких событий ≤1 тик; дополнительно показываем числа событий, TP/FP/FN/TN, результаты по таблицам, худшие задержки и неопределённость на малой выборке. Кандидат не должен ухудшать эти три метрики относительно действующей модели; при компромиссе — новый заранее согласованный протокол, без подгонки после test.

После проверки второй участник команды подтверждает отчёт и точный ID связки model/scaler; сохраняются старый ID, схема, эталон и результаты. Переключение выполняется явно, без fit при инференсе. На первом полном 72-часовом окне контролируем ошибки, свежесть и сигналы; при невозможности загрузки/несовместимости откатываем сразу, при подтверждённом нарушении критериев качества — после разбора. Откат выбирает прежний проверенный ID и его эталон, без переобучения. Если допущенной прежней модели нет, ML-выпуск блокируется; остаются явно обозначенная учебная демонстрация и правила мониторинга.

Baseline серии #9 имеет FPR **13,27%** на своём test: она не допущена и не считается безопасной точкой отката. Реестр #5 (`ml/model_registry.py`) хранит неизменяемые версии, переключает их только явной командой и без независимого test с тремя целевыми метриками не допускает версию. Ночное задание в 04:00 для источников с привязкой инференса (#12) при настроенном реестре кандидатов только обучает их, без активации; для остальных таблиц legacy-ветка по-прежнему перезаписывает joblib без этой процедуры. Учебная demo-модель Compose (#13) помечена `demo` и допуска качества не имеет: её метрики относятся к собственному синтетическому протоколу и не заменяют результаты #9. Первый допуск проходит по тем же порогам на независимом будущем test, без сравнения с действующей моделью. Метрики и уведомления — #16. #17 поставляет стратегию и проверяемый учебный сценарий, не выдаёт их за работающую автоматизацию.
