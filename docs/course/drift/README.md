## Что есть в коде и что предлагается

Сверено с master `aed9a6b` (08.11.2026, после слияния PR #37, #39, #40, #41):

| Область | Фактическое поведение | Предложение #17 / дальнейшая реализация |
|---|---|---|
| Признаки IF | `ml/features.py`: inner join `row_count`/`null_rate` по времени, разности с предыдущим согласованным наблюдением без нормировки по времени | Наблюдать все четыре входа отдельно, с полным source; разность через пропуск сбора исключать из статистики дрейфа (#16) |
| Валидация значений | `ml/features.validate_vector` проверяет конечность и физические границы входа инференса и реестра; `ml/drift.py` значения перед PSI/KS не проверяет | Та же проверка до KS/PSI; минимум и покрытие считать по валидным векторам; NaN/±Inf не дают `no_signal` |
| Дрейф колонок | `ml/drift.py`: старейший и новейший снимки за 7 дней; PSI >0,20/0,25, приблизительный KS p<0,05; одноимённые таблицы разных подключений объединяются | Фиксированный эталон входов IF, неперекрывающиеся окна, минимальная выборка/покрытие, подтверждение, раздельный source (#16) |
| Рост таблицы | Правила в коде нет; первая версия этой стратегии сравнивала уровень `row_count` с фиксированным эталоном, что даёт сигнал при любом росте | Уровень — только по коридору тренда эталона; норма роста — по `d_row_count`; выход за диапазон обучения — `expected_growth` |
| Данные распределений | `app/db.py`: top-20 значений, NULL исключены; сумма counts относится к top-N, не всей колонке | Не считать top-N полным распределением входов модели; использовать валидные векторы, одинаковые бины и полный охват |
| Недостаток данных | Один снимок даёт insufficient_data; пустые buckets могут дать PSI=0/KS p=1 | Проверять полноту до статистики. Нет данных не означает отсутствие дрейфа |
| Обучение | `collectors/scheduler.py`, 04:00: для источников с привязкой инференса при настроенном реестре обучаются только кандидаты, без активации; для остальных таблиц legacy IF перезаписывает joblib | Кандидат проходит проверку и явный выпуск; legacy-ветку не считать процедурой допуска |
| Версии и допуск | `ml/model_registry.py` (#5): неизменяемые версии, явный `activate`, `admitted()` требует независимый test, recall ≥0,8, FPR ≤0,1, задержку ≤1 тик | Те же пороги для кандидата; откат только к допущенной версии |
| Учебные модели | #9: исторический результат, FPR 13,27%, не допущена. Demo-модель Compose (#13, PR #41): `demo`, допуска качества нет, метрики — по [собственному протоколу](../containers/demo-model/RESULTS.md) | Не смешивать результаты #9 и demo-модели; ни одна не является точкой отката |

PSI на top-N и приближённый KS из текущего кода имеют ограничения. Порог p не гарантирует уровень ошибки на зависимых временных рядах. Четыре поправленных проверки не покрывают автоматически произвольное число колонок/таблиц. Предложенные окна и пороги требуют калибровки на независимых нормальных периодах; результат синтетической демонстрации такой калибровкой не является. Concept drift требует независимой разметки инцидентов; увеличение доли алертов — лишь косвенный сигнал.

## Воспроизведение сценария

Из корня репозитория с установленными зависимостями проекта. Сценарий к БД не обращается, но импорт настроек приложения требует `DATABASE_URL`:

```bash
DATABASE_URL=sqlite:////tmp/drift-unused.db python -m scripts.check_drift_strategy > /tmp/drift-demo.json
python -m pytest -q tests/test_drift_strategy.py tests/test_drift.py tests/test_scheduler_ml_retrain.py tests/test_schema_drift_per_project.py
```

[demo.json](demo.json) содержит фактический запуск с seed 42. Скрипт использует функции PSI/KS проекта на синтетической истории таблицы: `row_count` накапливает приращения N(5, 2) строк за 15 минут, `null_rate` независим. Это не временной ряд настоящей БД, не ML-эксперимент и не изменение production-политики. Сценарии после 14-суточного эталона, по два неперекрывающихся 72-часовых окна:

- обычный рост: KS/PSI уровня `row_count` против фиксированного эталона максимальны (D = 1), но приращения и коридор тренда в норме — `expected_growth`, устойчивого сигнала нет;
- скачок уровня на 2000 строк в середине первого окна: сигнал `row_count` по коридору в обоих окнах; `d_row_count` его не видит, так как скачок — одна разность из 288;
- рост темпа до 15 строк за тик: устойчивый сигнал и по `d_row_count`, и по коридору `row_count`;
- 199 векторов; пропуск сбора на 68 тиков (219 из 288) — `insufficient_data`;
- NaN, +Infinity, −Infinity в одном тике — `invalid_data`; NaN в 60 тиках оставляет 227 валидных векторов из 288 — `insufficient_data`.

Для проверки, что исход не определяется выбранным seed, те же три сценария повторены на seed 1000–1199 с неизменными порогами (`seed_sweep_1000_1199`): при обычном росте 6 из 200 историй дают одиночный сигнал в одном окне (повод для расследования), устойчивых сигналов 0; скачок и смена темпа дают устойчивый сигнал в 200 из 200. Коридор ±4σ√n и доля 10% — начальные настройки, заданные до прогона; величины скачка и темпа — заведомо крупные примеры, чувствительность к малым сдвигам не измерялась. Assertions проверяют ожидаемый исход; итоговое действие — расследование или проверенный кандидат, без автоматического переобучения. Обучения, переключения модели, БД и внешних вызовов нет. Числа в JSON округлены до 12 значащих цифр, чтобы порядок суммирования PSI не менял последние биты отчёта; решения принимаются до округления.

Результаты старого benchmark: [RESULTS](../experiments/RESULTS.md). FPR 13,27% сохраняется как отрицательный результат; этот PR не запускает новую серию и не меняет порог допуска 10%. Реестр версий (#5) и сервис инференса (#12) уже в master; подключение предложенной политики дрейфа к мониторингу — #16.

Результаты команд и проверка PDF записываются в [verification.json](verification.json). Код воспроизводимой сборки PDF: [render_pdf.py](render_pdf.py); нужен ReportLab и Unicode TTF-шрифт (пути передаются аргументами). PDF строится из STRATEGY.md, исходный текст остаётся доступен для ревью.
