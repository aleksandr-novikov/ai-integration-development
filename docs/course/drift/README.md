## Что есть в коде и что предлагается

Сверено с master `6ffaa6b` (25.10.2026):

| Область | Фактическое поведение | Предложение #17 / дальнейшая реализация |
|---|---|---|
| Признаки IF | `ml/anomaly_detector.py`: inner join метрик по времени, дельты до scaler | Наблюдать все четыре входа отдельно, с доказанным полным source (#12/#16) |
| Дрейф колонок | `ml/drift.py`: старейший и новейший снимки за 7 дней; PSI >0,20/0,25, приблизительный KS p<0,05 | Фиксированный эталон входов IF, неперекрывающиеся окна, минимальная выборка/покрытие, подтверждение (#16) |
| Данные распределений | `app/db.py`: top-20 значений, NULL исключены; сумма counts относится к top-N, не всей колонке | Не считать top-N полным распределением входов модели; использовать валидные векторы, одинаковые бины и полный охват |
| Недостаток данных | Один снимок даёт insufficient_data; пустые buckets могут дать PSI=0/KS p=1 | Проверять полноту до статистики. Нет данных не означает отсутствие дрейфа |
| Обучение | `collectors/scheduler.py`: ежедневный IF в 04:00; `train` берёт до 60 суток, min 200, перезаписывает joblib | Обучать кандидата, проверять и явно выпускать; интеграция с scheduler/API в #12 |
| Версии | PR #37 проверен отдельно, ещё не входит в указанную основу: реестр кандидатов и ручной откат | Использовать его после принятия; не вызывать отсутствующий API в этом PR |

PSI на top-N и приближённый KS из текущего кода имеют ограничения. Порог p не гарантирует уровень ошибки на зависимых временных рядах. Четыре поправленных сравнения не покрывают автоматически произвольное число колонок/таблиц. Предложенные окна и пороги требуют калибровки на независимых нормальных периодах; результат синтетической демонстрации такой калибровкой не является. Concept drift требует независимой разметки инцидентов; увеличение доли алертов — лишь косвенный сигнал.

## Воспроизведение сценария

Из корня репозитория с установленными зависимостями проекта:

```bash
python -m scripts.check_drift_strategy > /tmp/drift-demo.json
python -m pytest -q tests/test_drift.py tests/test_scheduler_ml_retrain.py tests/test_schema_drift_per_project.py
```

[demo.json](demo.json) содержит фактический запуск с seed 42. Скрипт использует функции PSI/KS проекта на независимых искусственных распределениях четырёх признаков. Это не временной ряд настоящей БД, не ML-эксперимент и не изменение production-политики. Сценарии: стабильные данные; устойчивый сдвиг только row_count в двух окнах; меньше 200 точек; 220 из 288 точек (достаточный минимум, недостаточное покрытие). Assertions проверяют ожидаемый исход, итоговое действие — расследование и проверенная обратная связь. Обучения, переключения модели, БД и внешних вызовов нет. Числа в JSON округлены до 12 значащих цифр, чтобы порядок суммирования PSI не менял последние биты отчёта; решения принимаются до округления.

Результаты старого benchmark: [RESULTS](../experiments/RESULTS.md). FPR 13,27% сохраняется как отрицательный результат; этот PR не запускает новую серию и не меняет порог допуска 10%. В стратегии описаны сравнение кандидата, независимый новый test и откат только к допущенной версии. Реальное переключение реестра проверяется в #5; подключение к сервису остаётся в #12.

Результаты команд и проверка PDF записываются в [verification.json](verification.json). Код воспроизводимой сборки PDF: [render_pdf.py](render_pdf.py); нужен ReportLab и Unicode TTF-шрифт (пути передаются аргументами). PDF строится из STRATEGY.md, исходный текст остаётся доступен для ревью.
