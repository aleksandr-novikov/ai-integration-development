# Мониторинг входных данных и работы модели Isolation Forest (#16)

Минимальный мониторинг одной опубликованной версии Isolation Forest для одного
источника: входные признаки, поведение модели, ошибки и время инференса, один
алерт качества. HTTP-метрики, логирование и технический алерт — в
[мониторинге сервиса (#15)](../README.md); PSI/KS, дрейф и переобучение — в
[стратегии #17](../../drift/STRATEGY.md). Здесь они не повторяются.

Код: [app/model_monitoring.py](../../../../app/model_monitoring.py) ·
сценарий проверки: [scripts/check_model_quality_alert.py](../../../../scripts/check_model_quality_alert.py) ·
фактический прогон: [demo.json](demo.json) ·
тесты: [tests/test_model_monitoring.py](../../../../tests/test_model_monitoring.py).

## 1. Наблюдаемые показатели

Все показатели относятся к **одному ряду**: `project_id`, `connection_id`,
`schema_name`, `table_name` + `model_version` + `feature_schema_version` + `demo`.
Одноимённая таблица другого подключения, другая версия и результаты другого
режима в ряд не попадают.

### Входы модели (`inputs`)

| Показатель | Как считается |
|---|---|
| `missing` по признаку | `row_count`, `null_rate`: моменты наблюдения, где значение отсутствует или не является конечным числом. `d_row_count`, `d_null_rate`: моменты без вычислимой разности с предыдущим согласованным наблюдением |
| `invalid_vectors` | Пары наблюдений, отклонённые `build_vector`/`validate_vector`: `not_a_finite_number` (NULL, NaN, ±Inf, текст) и `out_of_bounds` |
| `bounds` | Физические границы `validate_vector`: `row_count ≥ 0`; `0 ≤ null_rate ≤ 1`; предыдущий `row_count ≥ 0`; `−1 ≤ d_null_rate ≤ 1` |
| `distribution` | min, p05, медиана, p95, max, среднее, σ — **только по валидным векторам** |
| `freshness` | Время последнего валидного вектора и его возраст; предел — как у событий адаптера: `max(30 мин, 2 × интервал сбора)` |
| `valid_vectors`, `conclusive`, `reasons` | Вывод достоверен только при ≥ 20 валидных векторах, отсутствии невалидных значений и свежих данных. Иначе `conclusive: false` и причины: `no_valid_vectors`, `insufficient_valid_vectors`, `invalid_values`, `stale` |

Пропуски нулями не заполняются: пара с невалидной точкой исключается из
распределений и учитывается в `invalid_vectors`. Окно истории — 30 дней, как у
`source_storage.metrics`. Сравнение распределений с эталоном (PSI/KS) — задача
[#17](../../drift/STRATEGY.md).

### Работа модели (`model`)

| Показатель | Источник | Интерпретация |
|---|---|---|
| `scores.score` (min…max, p05/медиана/p95), `anomaly_rate` | `anomaly_scores` ряда за 30 дней | Распределение `decision_function`; `score < 0` ⇒ аномалия |
| `version`: `model_version`, `trained_at`, `age_days`, `origin`, `quality_admitted`, `labelled_evaluation` | Проверенный манифест реестра (`inspect_version`, без десериализации модели) | Для экспорта #9 время обучения не записано: `age_days: null`, `time_status: not_recorded_in_historical_export` |
| `inference.calls / ok / errors / error_rate` | `inference_predictions_total{source…, model_version, feature_schema_version, demo, outcome}` | `outcome` — `ok` или код ошибки адаптера: `inference_unavailable`, `model_unavailable`, `invalid_input`, `invalid_inference_response` и др. Отказы из-за входных данных до вызова (`insufficient_history`, `invalid_history`) видны в `inputs`, а не здесь |
| `inference.predict_seconds` (count, mean, p95 по границе корзины) | `inference_predict_duration_seconds` — значение `Server-Timing` сервиса | Только расчёт модели: без HTTP, авторизации и загрузки артефакта |

PromQL для внешнего Prometheus (если подключён):

```text
sum by (outcome) (increase(inference_predictions_total{model_version="<версия>"}[1h]))
histogram_quantile(0.95, sum by (le) (rate(inference_predict_duration_seconds_bucket{model_version="<версия>"}[1h])))
```

Счётчики живут в процессе Flask (интерактивные запросы и планировщик) и
обнуляются при его перезапуске, как и метрики #15.

## 2. Контроль качества модели

Precision, recall и FPR существуют только для данных с независимой разметкой.
Это результаты **двух разных экспериментов**, их нельзя смешивать.

| | #9, baseline (исторический benchmark) | #13, demo-модель Compose |
|---|---|---|
| Данные | Синтетический набор #7 (`dataset_id d217ec5f…`), три таблицы, шаг 15 мин; метки — расписание генератора | Синтетический режим `compose-demo-normal/1`; train только норма; метки — расписание генератора |
| Конфигурация | contamination 0,01, 100 деревьев, max_samples 256, seed 42 | `contamination_005`: 0,005, 100 деревьев, 256, seed 42 |
| Validation | 2016 наблюдений (1809 норм., 9 инцидентов): precision 35,22%, recall 42,03%, **FPR 8,84%** | 1600 векторов (1175 норм., 120 инцидентов): precision 92,3%, recall 100%, **FPR 0,85% (10/1175)** |
| Test (один раз) | precision 27,71%, recall 44,44%, **FPR 13,27% (240/1809)**, инциденты 9/9 | precision 89,4%, recall 100%, **FPR 1,66% (52/3133)**, инциденты 440/440 |
| Статус | **Цель FPR ≤ 10% не выполнена, допуск реестра не выдан** | Только `demo=true`, `quality_admitted=false`; область применимости 1–14 тыс. строк, 0–300 строк за сбор |
| Источник | [experiments/RESULTS.md](../../experiments/RESULTS.md), [summary.json](../../experiments/summary.json) | [demo-model/RESULTS.md](../../containers/demo-model/RESULTS.md), [selection.json](../../containers/demo-model/selection.json), [evaluation.json](../../containers/demo-model/evaluation.json) |

Precision/recall/FPR — по наблюдениям (тикам); FPR = FP / (FP + TN) на
нормальных тиках. Для версии из экспорта #9 отчёт показывает метрики её
`evaluation` (split, хеш данных, run_id) в `version.labelled_evaluation` и
`quality_admitted: false`.

**Текущий поток не размечен.** Precision/recall/FPR по нему не рассчитываются и
не подменяются предсказаниями самой модели. Используются косвенные показатели:
распределение score, доля аномалий против baseline той же версии, полнота,
валидность и свежесть входов, ошибки инференса. Они показывают, что поведение
детектора или входы изменились, но **не являются оценкой точности**.

## 3. Алерт `ModelAnomalyRateHigh`

| Параметр | Значение |
|---|---|
| Показатель | Число результатов с `is_anomaly = true` среди последних 20 результатов ряда |
| Окно | 20 последних результатов ряда (при сборе раз в 15 мин — 5 ч, на стенде с 5 мин — 100 мин). Окно счётное, чтобы статистическая сила правила не зависела от интервала сбора |
| Минимум данных | Полное окно, 20 результатов. Меньше — `insufficient_observations`, `condition: null`; состояние сохраняется: `inactive` не означает «норма», `firing` не снимается без полного окна |
| Baseline | Предсказания **этой версии** на нормальных размеченных тиках validation; совпадение источника, `model_version`, `feature_schema_version` и `demo` проверяется (`baseline_mismatch`); минимум 500 наблюдений (`baseline_insufficient`: при 0 аномалиях из 500 верхняя граница доли 0,76% — разрешение порядка contamination 0,5–1%); отсутствие — `baseline_missing`. Без применимого baseline правило не оценивается |
| Порог | Наименьшее k с P(X ≥ k) ≤ 1% для X ~ Bin(20, p), p — верхняя 95% граница Уилсона доли аномалий baseline |
| Порог для демо-версии | baseline **10/1175 = 0,85%** (validation #13, нормальные тики; test не использовался) → p = 1,56% → **k = 3 из 20 (15%)**; P(X ≥ 3) = 0,35%, P(X ≥ 2) = 3,8% |
| Срабатывание / восстановление | `firing` при k ≥ 3, `resolved`, когда в окне снова < 3; повторного события при том же состоянии нет |
| Сигнал | `app.alerts`: WARNING `alert_firing`, INFO `alert_resolved` с источником, версией, числом аномалий и порогом; поле `event` отчёта. Внешняя доставка не реализована |
| Ответственный | Инженер данных (по [MLOPS_ROADMAP](../../MLOPS_ROADMAP.md), М5); при подтверждении изменения поведения модели — ML-инженер (#17) |

Доля аномалий — не FPR: правило фиксирует, что детектор стал помечать заметно
больше точек, чем на нормальных данных validation. Это может быть реальный
инцидент, изменение режима источника или ухудшение модели; precision/recall это
не доказывает и не опровергает.

**При срабатывании.** 1) Открыть отчёт ряда: `inputs.conclusive`, `reasons`,
`invalid_vectors`, свежесть. Если входы недостоверны — сначала исправить сбор
(#15: логи коллектора, `collector_runs_total`). 2) По `/dashboard/inference`
найти аномальные точки окна и сравнить их `row_count`/`null_rate` и разности с
`inputs.features.*.distribution`: какой вход вышел за привычный диапазон.
3) Сверить с событиями источника (загрузки, откаты, миграции): подтверждённый
инцидент — записать как обнаружение, не как ложную тревогу. 4) Если инцидента
нет и доля держится выше порога — передать ML-инженеру для проверки дрейфа по
[#17](../../drift/STRATEGY.md); автоматического переобучения и переключения
версии нет. 5) Зафиксировать время, ряд и причину.

**При восстановлении.** Дождаться `alert_resolved`, убедиться, что
`inputs.conclusive: true`, и дописать в запись время восстановления и действия.

## 4. Как смотреть

Отчёт по ряду (JSON, один на итерацию; без `--iterations` — один раз):

```bash
python -m app.model_monitoring --source source.json --model-version <if-…> --demo \
  --baseline baseline.json --registry models/registry \
  --metrics-url http://127.0.0.1:5001/metrics --interval 300 --iterations 0
```

`source.json` — полный источник, как в привязке адаптера; `baseline.json` —
объект формата `build_baseline` для этой версии. Состояние алерта хранится в
процессе наблюдателя: после перезапуска первое полное окно выше порога снова
даст `firing`. Ряд score по-прежнему виден в `/dashboard/inference`.

## 5. Воспроизведение

Из корня репозитория с зависимостями `requirements-dev.txt`:

```bash
python -m scripts.check_model_quality_alert > docs/course/monitoring/model/demo.json \
  2> /tmp/model-alert-logs.jsonl
echo $?   # 0 — все проверки прошли
python -m pytest -q tests/test_model_monitoring.py
```

Сценарий (около 45 с, без сети и внешних сервисов): demo-модель #13
воспроизводится существующей процедурой (`scripts.demo_model`: train-сплит,
`train_candidate`, `contamination_005`, seed 42) для источника
`demo-project/demo-connection/public/events`; SHA-256 train и validation
сверяются с [selection.json](../../containers/demo-model/selection.json).
Baseline — эта версия на 1175 нормальных тиках validation #13. Поток источника —
генераторы строк и арифметика коллектора #13 с seed 4 000 000 (вне диапазонов
train/validation/test), сбор раз в 5 мин, старт 2000 строк:

- **норма** — 30 сборов по 0–300 строк; на 10-м сборе сервис инференса
  недоступен (проверка счётчика ошибок);
- **отклонение** — 6 сборов: три раза загружается пачка инцидента #13
  (10 × 200 строк аварийного генератора: 40% NULL `ip_address`, перекос
  `server-3`) и откатывается на следующем сборе;
- **восстановление** — 25 сборов нормы.

Каждый сбор: запись `row_count`/`null_rate` → реальный адаптер → FastAPI-сервис
(ASGI test client) → `anomaly_scores` → `report`. Параллельно пишутся данные
одноимённой таблицы другого подключения; они не должны попасть в ряд.

skops 0.16.0, локально без Docker. [demo.json](demo.json): `passed: true`,

побайтово детерминирован (см. [#13](../../containers/demo-model/RESULTS.md)).

- Повторная оценка тех же данных дважды — без событий; в журнале ровно две
  записи `app.alerts` (`alert_firing`, `alert_resolved`) с источником и версией.
- Baseline 400 наблюдений → `baseline_insufficient`, отсутствие →
  `baseline_missing`, другая версия или другой источник → `baseline_mismatch`;
  во всех случаях `condition: null` на окне, где основное правило сработало.
- В `anomaly_scores` 61 строка, все — `demo-connection`, одна версия, схема
  1.0.0, `is_demo=1`; данные `other-connection` (≈50 тыс. строк) в сводку входов
  не попали (62 момента наблюдения, max `row_count` 14 032).
- Инференс: 62 вызова, 61 `ok`, 1 `inference_unavailable` (1,6%); время
  вычисления — 61 измерение, среднее 10,6 мс, p95 ≤ 25 мс (граница корзины).
- Входы на конец прогона: 61 валидный вектор, пропусков и невалидных значений
  нет, данные свежие, `conclusive: true`.

**Предварительные прогоны того же сценария** (порог, окно и baseline не
менялись; результаты сохранены как факт о детекторе):

1. Отклонение — удаление 600 старейших строк на каждом сборе (`d_row_count`
   −300…−500): **0 аномалий из 6**; score снизился с 0,19–0,24 до 0,06–0,13, но
   остался положительным. Алерт корректно не сработал: сокращение таблицы
   такого масштаба детектор #13 не помечает.
2. Отклонение — пачки по 2000 строк **нормального** генератора с откатом:
   помечена только первая из трёх загрузок (score −0,033; далее +0,0002 и
   +0,012), 1 аномалия в окне, алерт не сработал. Isolation Forest не
   экстраполирует за обучающий диапазон `d_row_count` (0–300 строк за сбор), и
   при таблице 8–10 тыс. строк один лишь объём почти не выделяется.

Итоговое отклонение повторяет определение инцидента из протокола #13 (объём и
состав строк) вместо одного объёма.

**Тесты.** `python -m pytest -q tests/test_model_monitoring.py` — 38 passed:
сводки входов (полная, пропуски, NULL/NaN/±Inf/вне границ, пустая, короткая,
устаревшая история), разделение demo/обычных результатов, возраст и допуск
версии, `Server-Timing` реального сервиса и его разбор, счётчики вызовов, ошибок
и времени по версии, порог, переходы алерта, недостаточное окно, непригодный
baseline, изоляция источников и версий в хранилище.

## 7. Ограничения

- Демо-модель и baseline синтетические и учебные: `quality_admitted: false`.
  Для версии другого источника baseline строится заново из её собственных
  validation-предсказаний; переносить порог между версиями нельзя.
- Правило видит только то, что помечает детектор: при пропущенных моделью
  изменениях (предварительные прогоны 1–2) сигнала не будет. Отсутствие сигнала
  не доказывает отсутствие проблем.
- FPR demo-модели на test (1,66%) выше, чем на validation (0,85%); порог выбран
  только по validation. При устойчивом росте нормальной доли аномалий возможны
  ложные срабатывания — повод проверить дрейф (#17).
- Признак `row_count` — уровень таблицы: при росте за пределы области
  применимости модели (≈14 тыс. строк для #13) score систематически снижается;
  в конце прогона score нормальных тиков 0,10–0,12 против 0,19–0,24 в начале.
- Состояние алерта и счётчики Prometheus хранятся в памяти процесса; после
  перезапуска возможен повторный `firing`. Доставка в Telegram/почту не
  реализована.
- Время вычисления передаёт заголовок `Server-Timing`; старый сервис без него
  даёт только счётчик вызовов.
