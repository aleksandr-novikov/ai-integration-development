# MLOps-roadmap DB Monitoring на 6 месяцев

**Текущее состояние — уровень 0–1** (срез `cc77aab`, 24.10.2026). Унаследованы Flask, сбор/хранение метрик, [ночное обучение IF][scheduler], [Docker/Compose][compose], тесты и [CI][ci]. В курсе уже получены [данные с временным разделением и SHA-256][data], валидация, [5 MLflow-экспериментов + final_test][experiments] с git SHA/dataset_id/run_id и [проверки качества][quality]. Это отдельные элементы уровня 1, а сквозной управляемый ML-пайплайн отсутствует.

[Рабочий joblib][detector] перезаписывается, содержит модель/scaler и время, но не цепочку code/data/run; при отсутствии модели scoring вызывает обучение. В [сохранённых scores][storage] нет версии модели и идентичности подключения: источник конкретного прогноза полностью не восстановить. MLflow не публикует модель в приложение; откат образа не возвращает joblib из volume. [Технические метрики][metrics] и [PSI/KS распределений колонок][drift] не контролируют качество IF после выпуска. На test **FPR 13,27% > 10%**: baseline не получает допуска; зелёные тесты этого не меняют.

**Границы.** Учебный минимум — ещё открытые #4/#5 (контракт/версии), #11–#15 (тестовая стратегия, FastAPI ≥3 эндпоинта, запуск, выпуск, наблюдаемость), #16/#17 (качество/дрейф). #3 и #7–#10 закрыты; подробности — [план курса][course]. Ниже — предлагаемое развитие после или параллельно минимуму; М1–М6 обозначают месяцы от старта, не модули курса и не сроки семестра. Роли функциональные; персональные обязательства не назначаются.

**Четыре приоритетные практики:** **A — прослеживаемость** данных/моделей (утрата происхождения); **B — воспроизводимое обучение и допуск** (неудовлетворительный FPR); **C — управляемый выпуск/откат** (разрыв эксперимента и приложения); **D — мониторинг и переобучение** (незаметная деградация). Сначала A/B, затем C/D: приоритеты — данные, интеграция и мониторинг, с переиспользованием MLflow, pytest и текущего стека.

**Цель через полгода — уровень 1**, при выполнении плана: воспроизводимый логируемый пайплайн, обязательные проверки данных/признаков/качества, версии и испытанный откат; публикация и решение о переобучении остаются ручными. Мониторинг выявляет повод расследования, дрейф сам по себе не доказывает падение качества. При провале gate сохраняется предыдущая проверенная версия либо режим демонстрации. Улучшение ML-метрик не гарантируется. Один IF-кейс (модели по таблицам), четыре участника, частота плановых релизов не установлена: цена полной ML CI/CD уровня 2 пока не обоснована, несмотря на ночной retrain; пересмотр — при росте числа моделей, обновлений или стоимости ручных ошибок. Достаточен локальный/контейнерный контур; облачный production для зачёта не нужен.

**Год без практик — потенциальные последствия:** без A не восстановить происхождение/старый score; без B модель с уже выявленным превышением FPR может попасть в выпуск; без C несовместимые признаки и перезапись артефактов затруднят надёжный откат; без D деградация и нагрузка ложных сигналов останутся незамеченными при исправном сервисе. Это риски, а не утверждение о случившихся эксплуатационных инцидентах.
