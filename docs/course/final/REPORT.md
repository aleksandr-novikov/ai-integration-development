## 1. Бизнес-задача и назначение

**Проблема.** Нарушения качества данных часто не вызывают технического отказа БД: резко растёт доля NULL, нетипично меняется объём таблицы, ломается привычная динамика. Такие отклонения могут оставаться незамеченными, пока ошибочные данные не попадут в отчётность. Задача проекта — сократить время обнаружения таких инцидентов автоматическим анализом истории метрик ([CASE.md](../CASE.md)).

**Пользователь** — дата-инженер, аналитик данных или другой специалист, отвечающий за качество данных. Система указывает на подозрительное состояние, но не исправляет данные и не принимает решение вместо человека.

**Вход.** DB Monitoring периодически (по умолчанию раз в 15 минут) собирает по каждой таблице метрики: число строк, NULL-статистику, распределения, схему. Модель использует четыре признака: `row_count`, среднюю по колонкам долю NULL `null_rate` и их изменения между соседними наблюдениями `d_row_count`, `d_null_rate`.

**Выход.** Для наблюдения: объект мониторинга, время, значения признаков, признак «норма/аномалия», числовая оценка аномальности, версия модели. Результат показывается на дашборде, доступен через API и используется в уведомлениях.

**Роль ML.** Isolation Forest — метод без учителя: находит нетипичные наблюдения без ручного правила для каждого вида инцидента. Сигнал модели — повод для проверки человеком, а не доказательство ошибки. Детектор унаследован от исходного [DB Monitoring](https://github.com/aleksandr-novikov/db-monitoring) (коммит `1a869e4`); в курсе он превращён в воспроизводимый и проверяемый компонент: датасет, валидация, эксперименты, тесты, сервис, контейнеры, мониторинг и стратегия дрейфа.

**Критерии успеха** зафиксированы до экспериментов ([CASE.md](../CASE.md), раздел 7): обнаружено ≥ 80 % размеченных инцидентов; ложные сигналы — ≤ 10 % наблюдений вне инцидентов (FPR); медианная задержка обнаружения резких инцидентов ≤ 1 цикла сбора (15 минут).

## 2. Архитектура и технологический стек

Система — модульный монолит на Flask со встроенным планировщиком и отдельным сервисом инференса на FastAPI ([Architecture.md](../../Architecture.md), [ADR-001](../../adr/001-flask-and-inference-service.md)).

FastAPI не читает историю и не обучает модель: он проверяет токен, полный источник `(project, connection, schema, table)` и выбранную неизменяемую версию из реестра ([inference/README.md](../inference/README.md), [models/README.md](../models/README.md)). Три маршрута и Swagger UI проверены настоящим Uvicorn ([final-verification.md](../inference/final-verification.md)). Учебные MLflow-эксперименты не публикуют модель автоматически. Схема ниже отмечает реализованные компоненты [Р] и проектируемые [П].

## 3. ML-эксперименты и результаты

**Данные** ([DATASET.md](../DATASET.md)). Генератор с seed 42 создаёт синтетическую историю трёх таблиц (`users`, `orders`, `events`) с шагом 15 минут: 8 061 наблюдение, временное разбиение train 4 029 / validation 2 016 / test 2 016. Train содержит только нормальный режим. В validation и test по 9 размеченных инцидентов трёх типов: всплеск NULL, скачок объёма и смена режима. Дельты считаются только по предыдущему наблюдению того же ряда; scaler обучается только на train. Перед обучением выполняется валидация (20 проверок, раздел 4).

**Протокол** ([PROTOCOL.md](../experiments/PROTOCOL.md)) зафиксирован в Git до запусков (коммит `f94947c`). Пять конфигураций отличаются от baseline одним параметром. Правило выбора задано заранее: среди конфигураций, выполнивших все три цели на validation, взять максимальный F1 по наблюдениям. Test оценивается один раз, только для выбранной конфигурации, отдельным шестым run `final_test`. Precision, recall и F1 считаются по наблюдениям; обнаружение инцидента — хотя бы один сигнал внутри его интервала.

**Сравнение.** Наибольшее влияние из исследованных параметров оказывает `contamination`. Повышение до 0,05 даёт лучший F1 (+0,031), но FPR растёт до 24,49 % — конфигурация исключена правилом. Выводы локальные: один seed и однофакторные изменения.

**Вывод.** Модель **не прошла критерий допуска по ложным сигналам**, поэтому реестр не допускает её как рабочую. FPR вырос с 8,84 % на validation до 13,27 % на более позднем test. Гипотеза: абсолютный `row_count` растёт со временем и выходит из диапазона обучения; это не доказано. Медиана скрывает поздние сигналы: скачок объёма `users` найден через 5 циклов (75 минут), `orders` — через 2. Выбор после раскрытия test не менялся. Полный комплект — [MLflow-экспорт](../experiments/mlflow-export.zip) с пятью runs, `final_test`, моделями, предсказаниями и инструкцией импорта ([README](../experiments/README.md)); аудит по таблицам и типам — [quality/README.md](../quality/README.md).

**Отдельная demo-модель стенда.** Модель #9 для таблицы `events` обучена на `row_count` 56–68 тыс. На Compose-стенде с таблицей 2 000–5 200 строк она дала одинаковый score −0,077 всем точкам: векторы вне области обучения. Поэтому для стенда по отдельному протоколу, зафиксированному до test, на синтетическом режиме стенда заново обучена та же сетка из пяти конфигураций; по правилу #9 на validation выбрана `contamination_005` ([demo-model/RESULTS.md](../containers/demo-model/RESULTS.md)). На её собственном test: FPR 1,66 % (52/3 133), инциденты 440/440, сценарий Compose без ошибок в 190 из 200 эпизодов. Эта модель помечена `demo=true`, `quality_admitted=false`, не заменяет результат #9 и не является рабочей моделью.

## 4. Качество данных и тестирование

**Валидация данных** ([validation/README.md](../validation/README.md)). Скрипт на pandas проверяет манифест и SHA-256 файлов, схему CSV, типы и конечность, диапазоны (`null_rate` ∈ [0, 1], `row_count` ≥ 0), UTC-время, уникальность, порядок, непересечение выборок, полноту временной сетки, согласованность дельт и разметку. На исходном наборе — 20 проверок пройдено, 0 провалено. На намеренно испорченной копии (пустой идентификатор, текст вместо числа, выход за диапазон, время без UTC, дубликаты, перестановки и др.) — 14 проверок провалено. При ошибке обучение не начинается.

**Тест-план** ([testing/STRATEGY.md](../testing/STRATEGY.md)) построен по рискам:

Команда `check_model_quality` пересчитывает метрики из сохранённого архива #9 и для baseline **ожидаемо завершается кодом 1 (FAIL)**: зелёный pytest не означает допуск модели ([quality/README.md](../quality/README.md)). Проверка тест-плана в CI [PR #40](https://github.com/aleksandr-novikov/ai-integration-development/pull/40) (`39db8f6`): три `test`, `integration` и `ruff` — SUCCESS; локально 1 239 passed, 6 failed из-за окружения (нет `sqlite3` CLI и `python` в PATH), разбор — в [VERIFICATION.md](../testing/VERIFICATION.md).

**Выявленные проблемы и риски.**

- **Высокий FPR baseline** — 13,27 % на test (раздел 3). Допуск не выдан, критерий не ослаблен.
- **Модель вне области обучения.** На CI архивная модель #9 пометила аномалией все нормальные тики стенда: масштаб таблиц стенда далёк от данных обучения. При разборе найден и независимый дефект: генератор `live_demo` не заполнял две колонки и поднимал `null_rate` в «норме». Генератор исправлен, для стенда обучена отдельная demo-модель ([demo-model/PROTOCOL.md](../containers/demo-model/PROTOCOL.md)).
- **Вероятностная нестабильность demo-модели.** Нормальный поток стенда генерируется без фиксированного зерна, и по test сценарий проходит в 190/200 случаев (95 % ДИ 0,91–0,97): примерно один прогон из 20 даёт ложную тревогу. Это наблюдалось в [PR #46](https://github.com/aleksandr-novikov/ai-integration-development/pull/46): в [run 42674706790](https://github.com/aleksandr-novikov/ai-integration-development/actions/runs/42674706790) job `integration` упал на `check-outcome` (`false_alarms 1` из 3 нормальных тиков, инцидент найден), повторная попытка на том же HEAD `62b9f4a` прошла. Это ограничение качества модели, а не неисправность системы. Один успешный повтор не доказывает отсутствие нестабильности; порог и зерно ради PASS не подбирались.
- **Нестабильность самой проверки.** Окно наблюдения Compose-сценария открывалось с микросекундами, а метки метрик хранятся с точностью до секунды, из-за чего тик мог выпасть (HEAD `d8f65f4`). Исправлено, добавлены регрессионные тесты ([containers/verification.md](../containers/verification.md)).

## 5. Деплой и мониторинг

**Маршрут запуска** ([containers/README.md](../containers/README.md)). `Dockerfile` и `docker-compose.yml` поднимают PostgreSQL-источник, TimescaleDB-хранилище и Flask-приложение со сборщиками; профиль `inference` добавляет FastAPI на том же образе с реестром только для чтения. `scripts.init_compose_demo` создаёт `.env` без внешних ключей (NIM и Telegram пусты), порты публикуются только на `127.0.0.1` (Flask 15001, FastAPI 18000). Далее — seed демонстрационной БД, обучение demo-модели, запуск инференса и `curl /healthz`. CI выполняет этот маршрут из чистого checkout: сборка `nocache`, readiness, нормальные тики, инцидент, перезапуск БД с проверкой сохранности данных. Docker в среде разработки отсутствовал, поэтому Compose проверялся только в CI. Независимый ручной прогон человеком, не участвовавшим в разработке, **не выполнен** (критерий 7 в [verification.md](../containers/verification.md)).

**Стратегия релиза и отката** ([deployment/STRATEGY.md](../deployment/STRATEGY.md), #14) — **проектное решение**. Для приложения целевой подход — blue-green. На стенде нет двух сред и переключателя трафика, а планировщик стартует в каждом процессе Flask. Поэтому предложено проверять green в изолированном Compose-проекте на копии данных и затем заменять контейнер между тиками. Для модели — shadow, затем canary по источникам через привязки версий. Реализованы CI, реестр с допуском, привязки и оценки с ключом версии, алерты. `release.yml` и runbook отката есть в коде, но не запускались. Переключатель трафика, shadow-оценка и откат **не реализованы и не испытаны**. Этап допуска модели сейчас заканчивается «СТОП»: допущенной модели нет.

**Технические метрики** ([monitoring/README.md](../monitoring/README.md), #15): `/healthz` с пробами зависимостей; `/metrics` в формате Prometheus — `http_requests_total`, гистограмма `http_request_duration_seconds` (p95), `collector_runs_total`; JSON-логи с `request_id`; маскирование секретов, в том числе в traceback (дефект найден и исправлен в #15). Эскиз дашборда из 10 панелей — [DASHBOARD.md](../monitoring/DASHBOARD.md). Prometheus-сервер и Grafana не развёрнуты.

**Показатели данных и модели** ([monitoring/model/README.md](../monitoring/model/README.md), #16) считаются по одному источнику и одной версии. Входы: пропуски и невалидные значения каждого признака, распределения, свежесть, признак достоверности вывода `conclusive`. Модель: распределение score, доля аномалий, версия и допуск, ошибки инференса `inference_predictions_total{outcome}`, время расчёта (`Server-Timing`). Текущий поток не размечен, поэтому precision/recall по нему не считаются. **Дрейф** ([drift/STRATEGY.md](../drift/STRATEGY.md), #17): 72-часовое окно против 14-суточного эталона; KS: D ≥ 0,10 и p < 0,0125; PSI > 0,20 — предупреждение, > 0,25 — сильный сдвиг. Для растущего `row_count` используется коридор тренда. Переобучение — по событию с ручным допуском; эти правила описаны и проверены синтетическим сценарием, но не автоматизированы.

|---|---|---|
| `HttpErrorRatioHigh` | Доля 5xx > 10 % за 5 минут при ≥ 10 запросах | Сценарий «норма → сбой БД → восстановление»: `firing` на 4-м тике сбоя, `resolved` на 7-м тике восстановления; повтор против живого сервера ([demo.json](../monitoring/demo.json)) |
| `ModelAnomalyRateHigh` | ≥ 3 аномалий среди 20 последних результатов ряда; порог выведен из baseline 10/1 175 на validation demo-модели | `firing` на тике 33, `resolved` на тике 54, 19 проверок `true` ([demo.json](../monitoring/model/demo.json)) |

Таблица 3. Алерты пишутся в журнал `app.alerts`. Доставка во внешний канал (Telegram, почта) не реализована.

## 7. Ограничения, выводы и развитие

**Существенные ограничения.**

- **Синтетические данные.** Все метрики качества получены на сгенерированных наборах: 9 инцидентов в test #9, отдельный режим demo-модели. Перенос на реальные БД не доказан.
- **Модель.** Baseline не выполнила цель FPR ≤ 10 % (13,27 %); demo-модель стенда допуска не имеет и вероятностно даёт ложную тревогу примерно в 1 сценарии из 20. Четыре признака чувствительны к росту абсолютного объёма таблиц.
- **Дрейф.** Рост таблиц выводит векторы из области обучения, что уже наблюдалось на стенде. Пороги KS/PSI — начальные настройки, их эффективность на реальном потоке не измерена. Автоматического переобучения нет.
- **Границы автоматизации.** Модель и LLM дают сигнал и гипотезу, решение принимает специалист. Алерты не доставляются во внешний канал; Prometheus-сервера нет.
- **Деплой.** Blue-green, shadow/canary и откат описаны, но не испытаны; `release.yml` не запускался; независимый ручной прогон стенда не выполнен.
- **Прототип, не production.** Планировщик внутри процесса Flask без распределённой блокировки, нет HA и очередей, часть legacy-маршрутов API сохраняет прежний режим доступа.

**Вывод.** На базе DB Monitoring построен воспроизводимый учебный контур ИИ-компонента. В него входят: синтетический датасет с разметкой и временным разбиением, валидация из 20 проверок, пять зафиксированных экспериментов MLflow с одной честной оценкой на test, тесты модели и CI, FastAPI-сервис с реестром версий, Compose-стенд, проверенный в CI, технический алерт и алерт модели. Главный результат по качеству отрицательный, и он зафиксирован: модель находит все 9 инцидентов test с медианной задержкой 0 циклов, но даёт 13,27 % ложных сигналов и потому не допущена к эксплуатации.

**Предложения по развитию** (не выполнены): новая заранее объявленная серия экспериментов с признаками, устойчивыми к росту таблиц, и новым закрытым test; оценка на реальной истории с подтверждёнными инцидентами; доставка алертов и Prometheus-сервер; испытание отката по runbook; независимый прогон стенда другим участником.
