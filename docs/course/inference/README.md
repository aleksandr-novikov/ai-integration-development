# FastAPI-инференс — задача #12

Сервис предоставляет `GET /healthz`, `POST /v1/model`, `POST /v1/predict` и
Swagger UI `/docs`. Он проверяет токен, полный источник и неизменяемую версию
scaler/Isolation Forest из [реестра](../models/README.md). Обучение, чтение
истории и запуск планировщика в HTTP-сервисе отсутствуют.
[Контракт OpenAPI 3.1](../api/inference.openapi.yaml) общий для сервиса и адаптера;
он входит в Docker-образ, проверяется при сборке и загружается один раз на процесс.

## Запуск и Swagger UI

Из корня репозитория, Python 3.11–3.13. Для **обслуживания** достаточно
`requirements-inference.txt`. Для **экспорта** нужны также pandas и его зависимости;
отдельный набор позволяет воспроизвести экспорт без Flask и MLflow:

```bash
python -m pip install -r requirements-model-export.txt
python -m scripts.model_versions --registry models/registry stage-export \
  --source docs/course/inference/source.example.json
```

Команда выводит манифест с `model_version`. Архивный baseline #9 не прошёл
допуск качества, поэтому пример обслуживается только в явном режиме `demo`.
Скопировать [service.example.json](service.example.json), указать полный source
и полученную версию в запросах Swagger:

```bash
export INFERENCE_ADAPTER_TOKEN="$(openssl rand -hex 32)"
export INFERENCE_CONFIG=docs/course/inference/service.example.json
python -m uvicorn inference.service:create_app --factory --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000/docs`, нажать Authorize, ввести токен и выполнить
три маршрута. `/v1/model` принимает source и обе версии; `/v1/predict` — также
готовые признаки и время текущего/предыдущего наблюдения. `/healthz` проверяет
процесс, доступность конкретного артефакта проверяется через `/v1/model`.
Без разрешённых токенов модель недоступна. Секреты хранятся в переменных
окружения. За пределами локального стенда требуется TLS.

Реестр — доверенная директория оператора. Контрольная сумма обнаруживает
повреждение артефакта, но не заменяет подпись поставщика. Артефакт и свидетельства
допуска проверяются и после прогрева кэша. Загрузка и хэширование выполняются
вне общей блокировки кэша, поэтому независимые источники не сериализуются ею.

## Flask, объяснения и права доступа

1. Создать проект и подключение через UI. Примерные ID автоматически не создаются.
2. Опубликовать модель для полного source, включить его в allowlist сервиса и
   в копию [adapter.example.json](adapter.example.json). Указать настоящие версии.
3. Задать `INFERENCE_ADAPTER_CONFIG` и переменную токена адаптера. Значение `demo`
   должно совпадать с сервисом; адаптер сверяет source, версии и время ответа.
4. Собрать минимум две согласованные точки `row_count`/`null_rate` сборщиком подключения.
5. Открыть «Версии оценок» (`/dashboard/inference`), выбрать источник и пару версий.
   Запуск предсказания разрешён владельцу/редактору; viewer может читать результаты.

Просмотр объяснения не требует ML-bindings. `/api/explain` проверяет сессию,
текущий проект, активное подключение, namespace, историю обеих метрик и только
затем читает кэш. UI передаёт source выбранной аномалии и CSRF-токен. Запрос
`{table, metric, ts}` также поддерживается: сервер определяет источник по
актуальным подключениям и фактическому наблюдению. Несколько подходящих
источников дают 409 `source_required`; чужой/удалённый источник — 403.
История удалённого подключения никогда не приписывается новому подключению.

Кэш LLM изолирован ключом `(project_id, connection_id, schema_name, table_name,
metric, ts)`. Объяснения описывают фактические метрики на момент наблюдения;
они не являются доказательством причин инцидента. При недоступности NIM
действуют правила. Сравнение времён типизированное, с UTC и сохранением
микросекунд; legacy-контекст содержит фактический score. Сохраняются ограничения
[LLM-аудита](../LLM_LIMITATIONS.md).

Невалидные временные метки/значения истории дают 422 `invalid_history`;
неоднозначные наблюдения интерактивных маршрутов — 409 `ambiguous_source`.
Эти проверки предшествуют обращению к кэшу/LLM. Неверное время запроса
отличается от повреждённой истории и даёт клиентскую ошибку валидации.

FastAPI принимает строгий JSON, конечные числа и RFC 3339 (runtime-зависимость
`rfc3339-validator` обязательна). Максимальный размер тела — 64 KiB, глубина — 32.
Превышение размера даёт 413 `request_too_large`, слишком глубокий/некорректный JSON —
400 `invalid_json`. Ошибки сервиса используют единый JSON-конверт.

## Фоновая обработка и выбор версии

На каждом тике история каждой метрики читается один раз на источник. Адаптер
строит пары наблюдений и вызывает сервис только для отсутствующих результатов
полного ключа `(project_id, connection_id, schema_name, table_name, ts,
model_version, feature_schema_version)`. Повторный тик без новых точек не
отправляет предсказания. В пределах проекта переиспользуется один HTTP-клиент.
Валидаторы контракта кэшируются без общего изменяемого состояния запросов.

Дубликат изолирует свою точку и следующую пару; повреждённое время пропускается
с записью в журнал. Последующие корректные пары и другие источники продолжают
обрабатываться. Исторические записи не удаляются. Ошибки модели/доступа/сервиса
останавливают оставшиеся точки только соответствующего источника. Неожиданные
ошибки передаются заданию как `ExceptionGroup` после попытки остальных источников;
`MemoryError` немедленно прерывает обработку. Повреждённая конфигурация даёт
503 `invalid_configuration` и явную запись в журнал, без разрешающего fallback.
Ошибка задания проекта не прерывает цикл независимых проектов.

Новая аномалия сохраняется атомарным `INSERT ... ON CONFLICT DO NOTHING`, затем
вызывает настроенное Telegram-уведомление с обычным throttling. Повторный тик
или конкурирующая вставка того же ключа не отправляет уведомление повторно.
Доставка не транзакционна с БД: сбой процесса после записи может потерять
уведомление; гарантированная доставка требует отдельного transactional outbox.

«Обзор», «История» и основной API аномалий читают выбранную в `bindings` пару
версий каждого полного источника. Раздел «Версии оценок» позволяет явно прочитать
другую пару. Переключение/откат — изменение `model_version`/`feature_schema_version`
в `bindings`; новые версии получают собственный backfill, старые результаты
сохраняются и повторно используются при откате. Команда реестра `activate`
меняет указатель для его CLI, но не переключает явно заданные версии адаптера.

Источники без опубликованной модели сохраняют legacy-механизм. Legacy-результаты
не получают версию активной модели и не суммируются с ней. Legacy-детектор
различает проект/имя таблицы, но не подключения: при совпадении имён таблиц
переводить их следует вместе, явно задав все источники в bindings. Безопасный
раздельный legacy-скоринг одноимённых таблиц требует отдельной доработки.

При заданном `candidate_registry_path` и `INFERENCE_TRAINING_GIT_SHA` ночное
задание может обучать кандидатов из >=200 согласованных векторов. Ошибка одного
источника не отменяет обучение остальных и скоринг выбранных моделей. Кандидат
не активируется автоматически и требует отдельного допуска качества.

## Миграции и удаление данных

Существующие scores сохраняются с маркерами `legacy-unknown`; версия и владелец
не угадываются. Старые объяснения получают `legacy-unowned` и недоступны
обычным запросам. Миграция вызывается при первом получении движка. PostgreSQL
сериализует весь цикл проверки/DDL session advisory lock; внутри SQLite действует
блокировка процесса. Это не заменяет остановку писателей при обновлении.

Обязательный порядок резервного копирования, проверки и восстановления, а также
задача по эксплуатационным миграциям — [migrations.md](migrations.md).
После появления нескольких версий откат только приложения на старую схему
небезопасен. Реальная TimescaleDB требует отдельной приёмки миграций.

Удаление проекта транзакционно очищает связанные метрики, scores, схемы,
LLM-кэш и уведомления, включая таблицы без внешнего ключа. Чужие проекты
не затрагиваются.

## Проверки и измерения

```bash
python -m pytest -q
python -m pytest -q -m integration tests/integration/test_inference_migration.py
python -m pytest -q -m e2e
python -m openapi_spec_validator docs/course/api/inference.openapi.yaml
python -m scripts.inference_smoke --output /tmp/inference-evidence --swagger
python -m ruff check .
python -m pip check
```

Интеграционные тесты требуют Docker. Браузерные тесты требуют Chromium и
Playwright; штатная установка — `python -m playwright install chromium`.
Для установленного отдельно Chromium можно задать
`PLAYWRIGHT_CHROMIUM_EXECUTABLE=/путь/к/chrome` для E2E и Swagger smoke;
версию браузера следует записать в отчёт. Smoke запускает настоящий uvicorn и проверяет Swagger в браузере; NIM,
Telegram и рабочие БД не используются. SQLite CLI нужен тестам backup/restore.

Актуальные результаты повторного ревью и измерений: [review-acceptance.md](review-acceptance.md).
[Первоначальные измерения](evidence/smoke.json),
[исторический отчёт N-5/N-6](evidence/pr39-quality.json) и
[предыдущие регрессии](evidence/review-fixes-followup.json) сохранены как
исторические свидетельства; они не подтверждают текущее состояние CI.
Конфигурации и реестр для контейнера передаются отдельными mounts; пути
`INFERENCE_CONFIG`/`INFERENCE_ADAPTER_CONFIG` должны указывать на эти mounts.
Примерные конфигурации и архив обучения не входят в runtime image.
Ни один локальный замер не является SLA или подтверждением качества demo-модели.

Измерение накладных расходов адаптера (временная SQLite, HTTP-ответ без исполнения
модели/сети):

```bash
DATABASE_URL=sqlite:// python -m scripts.benchmark_inference_adapter \
  --baseline-ref db88c2aa90b8e8dc0c276bd371101b64b9e10a1f \
  --output /tmp/inference-adapter-benchmark.json
```

Сравниваются прежний адаптер/валидатор и текущие при одном читателе истории.
Каждый сценарий включает первый тик, повтор и две новые точки на источник.
В наборе из 2880 сохранённых точек пять находятся за 30-дневной границей;
при первом тике оцениваются 2874 пары. Нагрузка на чтение окна остаётся линейной,
но повторные предсказания и разбор контракта исключены.
