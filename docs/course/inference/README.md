# FastAPI-инференс — задача #12

Реализованы `GET /healthz`, `POST /v1/model`, `POST /v1/predict` и Swagger UI
`/docs`. Сервис не импортирует Flask, хранилище метрик или планировщик и не
обучает модель на запросе. Он получает готовые признаки, проверяет токен и
полный источник, загружает выбранную неизменяемую пару scaler/Isolation Forest
из [реестра #5](../models/README.md), возвращает score и фактические версии.
Контракт — [API 1.1.0, OpenAPI 3.1](../api/inference.openapi.yaml), маршрут остаётся `/v1/`.

## Запуск и Swagger UI

Из корня репозитория, Python 3.11–3.13:

```bash
python -m pip install -r requirements-inference.txt
python -m scripts.model_versions --registry models/registry stage-export \
  --source docs/course/inference/source.example.json
```

Команда выводит манифест с `model_version`. Пример использует архивный baseline
#9: его качество не прошло допуск, поэтому далее **только явный режим demo**.
Сохранить версии и исходные данные нового эксперимента можно через CLI #5;
обычный сервис с `demo=false` принимает только положительно допущенные модели.

```bash
export INFERENCE_ADAPTER_TOKEN="$(openssl rand -hex 32)"
export INFERENCE_CONFIG=docs/course/inference/service.example.json
python -m uvicorn inference.service:create_app --factory --host 127.0.0.1 --port 8000
```

В браузере открыть `http://127.0.0.1:8000/docs`, нажать Authorize и ввести токен.
У `/v1/predict` выбрать Try it out, заменить пример `model_version` на ID из
манифеста, выполнить Execute. Для `/v1/model` передать только `source`,
`model_version`, `feature_schema_version`. `/healthz` доступен без токена:
он проверяет процесс; доступность конкретной модели проверяет `/v1/model`.
В Swagger используется текущий адрес сервера, а не жёстко заданный порт 8000.

Без конфигурации разрешённых токенов запросы к модели получают 401.
Секреты находятся в переменных окружения; JSON содержит только имена переменных.
Вне локального изолированного стенда нужен TLS. Реестр — доверенная директория
оператора: SHA-256 обнаруживает повреждение, но не заменяет подпись поставщика.

## Flask, сборщики и дашборд

1. Создать проект и подключение обычным UI приложения. В копиях примерных
   конфигураций указать их реальные ID, схему/namespace и таблицу. Значения
   `project-a`/`connection-a` — примеры, эти записи автоматически не создаются.
2. Опубликовать модель именно для этого полного source, обновить allowlist
   сервиса и `bindings` в копии [adapter.example.json](adapter.example.json).
   Заменить `REPLACE_WITH_STAGED_VERSION` на реальный ID.
3. Для Flask задать `INFERENCE_ADAPTER_CONFIG=/путь/adapter.json` и тот же
   `INFERENCE_ADAPTER_TOKEN`. Режим `demo` должен совпадать с сервисом: адаптер
   отклоняет ответ при несовпадении режима или source/версии/времени.
4. Выполнить сбор минимум двух согласованных точек `row_count`/`null_rate`
   обычным сборщиком подключения. Старой истории нельзя приписывать источник.
5. Войти в проект, открыть **«Версии оценок»** (`/dashboard/inference`), выбрать
   источник и пару версий. Кнопка оценивает последнюю согласованную точку через
   `POST /api/inference/predict`; показанные строки читаются из БД именно по
   выбранной паре. Демо-режим сохраняется с результатом и виден после смены
   текущей конфигурации. Старые результаты `legacy-unknown` показаны отдельно.

Адаптер использует общую чистую `ml.features.build_rows`, сопоставляет UTC-время,
не заполняет пропуски нулями. Нет предыдущей точки — 422 `insufficient_history`;
дубликаты одного наблюдения одного источника — 409 `ambiguous_source`.
Это относится к `/api/inference/predict` и `/api/inference/metrics`;
неизвестные ошибки `ValueError` не классифицируются как конфликт истории.
Нечисловые значения истории, а также `NaN`/`Infinity` в признаках дают 422
`invalid_history` до HTTP-запроса: такие значения в сервис не передаются.
Перенос истории из другого подключения или угадывание владельца запрещены.

`/api/inference/sources`, `/scores`, `/metrics` требуют авторизованного пользователя
и текущего доступного проекта. `/scores` требует обе версии; пользователь не
получает права передачей `project_id`. Проверяются активное подключение,
схема/namespace и явный allowlist. Для POST из браузера используется CSRF-токен.

Периодический скоринг выбранных в `bindings` источников вызывает тот же сервис и
сохраняет версии из его ответа. Ошибка истории/признаков, отказ инференса или
временная ошибка хранилища записываются в журнал с полным `source` и traceback;
обработка продолжается со следующего источника. Отказ, относящийся к одному
наблюдению (`invalid_history`, `insufficient_history`, `invalid_input`),
пропускает только эту точку с предупреждением; отказ модели, схемы признаков,
доступа или сервиса прекращает обработку оставшихся точек этого источника.
`model_version` и `feature_schema_version` из `bindings` проверяются по контракту
до чтения истории и HTTP-запросов: неверное значение — ошибка источника
`invalid_binding`, по нему не отправляется ни одной точки.
Неожиданные ошибки получают примечание с `source` и после попытки обработать все
источники передаются вызывающему заданию одним `ExceptionGroup`; планировщик
один раз записывает его в журнал для проекта со всеми traceback. `MemoryError`
сразу прекращает обработку источников проекта (уже собранные неожиданные ошибки
перед этим записываются в журнал) и передаётся заданию; задания `scheduler` и
`per_project` перехватывают `Exception`, поэтому регистрируют её как ошибку
проекта и продолжают работу, а не останавливаются. Сбой не переключает модель и не удаляет ранее
сохранённые оценки; сохраняются только полностью проверенные ответы сервиса.
Ночное задание не обучает для них старый mutable
joblib. При заданном `candidate_registry_path` в конфигурации адаптера и
`INFERENCE_TRAINING_GIT_SHA` оно может создавать новые кандидаты из >=200 точек;
кандидат не меняет выбранную версию и требует отдельной оценки/публикации.
Ошибка обучения кандидата не должна отменять скоринг уже выбранной модели.
Для других имён таблиц legacy продолжает прежнюю работу. Если в проекте
совпадают имена таблиц разных подключений, включение нового контура для одного
из них отключает legacy-скоринг этого имени: старый детектор не различает
подключения. Нужные источники следует явно включить в bindings. Старый раздел дашборда
читает только `legacy-unknown`, не суммирует оценки новых моделей.

Переключение/откат — явное изменение `model_version` в `bindings`; сервис не
подставляет последнюю модель. Входной токен авторизует полный source, а версия
проверяется по source в манифесте. История предыдущей версии остаётся в БД.

## Миграции и LLM

При инициализации хранилища применяется идемпотентная миграция SQLite/PostgreSQL:

- `anomaly_scores`: ключ `(project_id, connection_id, schema_name, table_name,
  ts, model_version, feature_schema_version)`; старые версии и неизвестный
  источник получают `legacy-unknown`, значения score сохраняются.
- `metrics`: новые строки сборщика получают ID подключения и полную схему;
  старые строки остаются без атрибуции (`legacy-unknown`). Метаданные схемы
  новых источников хранятся отдельно в `source_schema_snapshots`.
- Кэш LLM получает ключ `(project_id, connection_id, schema_name, table_name,
  metric, ts)`. Старые объяснения сохранены с владельцем `legacy-unowned` и
  недоступны обычным запросам. TTL и upsert учитывают полный ключ.
- [Перенос SQLite → Timescale](../../../scripts/migrate_metrics_to_timescale.py)
  сохраняет новые ключи и маркеры, включая режим демонстрации.

Перед обновлением рабочей БД нужен обычный backup и остановка писателей на время
смены ключей; проверка выполнена на отдельных временных базах. Уже перезаписанные
исторические результаты миграция не восстанавливает.

`POST /api/explain` проверяет сессию, типы полей, время и доступ **до чтения кэша**.
Неоднозначная история выбранного источника возвращает 409
`{"error":"ambiguous_source"}` до обращения к кэшу и LLM. Проверяются обе метрики
контекста (`row_count` и `null_rate`) за используемое объяснением окно времени.
Для данных с известным подключением требуется полный `source`. Контекст/схема
читаются только для него; старый проектный путь не читает схему `legacy` другого
проекта. Прямой путь Telegram выбирает только однозначный явно записанный источник;
при неоднозначности возвращает правила с просьбой выбрать источник, без NIM.
Три прежних XFAIL #18 стали обычными регрессионными тестами. Это исправляет
изоляцию, но не делает LLM-гипотезы доказанными причинами и не устраняет prompt
injection/галлюцинации; исходный [аудит #18](../LLM_LIMITATIONS.md) сохранён.

Последняя команда требует development-зависимостей и `python -m playwright
install chromium`. Она запускает отдельный uvicorn, выполняет три запроса через
настоящий Swagger UI в Chromium, сохраняет скриншоты и 100 измерений HTTP.
Токен временный и исключён из сохраняемых запросов/скриншотов; реальные NIM,
Telegram и рабочие БД не используются.

Фактические запросы/ответы, окружение, холодный запрос, p95 по ближайшему рангу,
все измерения и ошибки — [evidence/smoke.json](evidence/smoke.json).
Скриншоты: [health](evidence/swagger-health.png),
[model](evidence/swagger-inspectModel.png), [predict](evidence/swagger-predictAnomaly.png).
Прогретая модель кэшируется по source и неизменяемой версии; перед каждым
использованием проверяются актуальные манифест и байты артефакта. Повреждение
даёт 503 даже после прогрева. Измерения относятся к одному worker на локальном
хосте без лимита ресурсов, исключают Flask/историю; это не проверка доступности
за период или SLA на предложенном профиле 2 vCPU/4 GiB. Итоги тестов и саморевью —
[verification.json](verification.json).

Docker/Compose и схема развёртывания относятся к #13; положительный допуск новой
ML-модели выполняется отдельно и не подменяется успешным HTTP-тестом демо-модели.
