## Ограничения и безопасное продолжение

**Смешанный legacy/ML для одноимённых таблиц.** Старые чтение истории, mutable
модель и её путь используют project/table. Включение одной полной ML-привязки
отключает legacy для этого имени, чтобы не смешивать источники. Произвольный
перезапуск legacy по второму подключению использовал бы чужую историю/модель;
такое исправление небезопасно. До доработки все одноимённые источники следует
явно включать в bindings с собственными допущенными моделями либо не включать
новый контур для этого имени. Это оставляет Д-3 частично открытым.

Отдельная техническая задача: передать полный source в legacy feature builder,
обучение, пути mutable-артефактов и фоновые задания; новые legacy-оценки хранить
с полным source и маркерами версии. Старые артефакты/строки нельзя автоматически
перепривязывать. Приёмка: два подключения с одинаковой таблицей, модель только
у одного; оба независимо оцениваются/уведомляют, история и UI не смешиваются,
старые артефакты сохранены. Требуется отдельное согласование этой переработки.

**Миграции.** PostgreSQL advisory lock защищает конкурирующие новые workers;
отсутствуют полноценный versioned migration runner, общий атомарный upgrade
и межпроцессный migration lock SQLite. Окно обслуживания, backup и репетиция
обязательны. Прямой downgrade старым приложением после нескольких версий
небезопасен. [Runbook и отдельная техническая задача](migrations.md) содержат
порядок восстановления в отдельную БД, включая TimescaleDB. Рабочие данные
не мигрировались. Реальная TimescaleDB остаётся проверкой перед развёртыванием.

**Доставка.** Telegram вызывается после сохранения, не является одной транзакцией
с БД. Для гарантированной повторяемой доставки после сбоя процесса нужен outbox.
Идемпотентный пересчёт не повторяет уже обработанные ключи.

**Активация.** В адаптере источником выбора остаются bindings. Указатель `activate`
реестра используется его CLI и автоматически не переключает явные версии сервиса.
Это различие документировано; автоматическая смена выбранной версии не добавлялась.

Повторное ревью исправлений возможно; полное закрытие задания и эксплуатационная
приёмка требуют решения смешанного legacy-сценария и успешных проверок
реальных БД/образа для целевого окружения. Draft-состояние PR сохраняется.
