# Безопасное обновление хранилища инференса

Миграция изменяет ключи scores и LLM-кэша. Она сохраняет строки, но после записи
нескольких версий старый код не может восстановить прежний первичный ключ без
потери данных. Автоматическая обратная миграция не предусмотрена.

## Порядок обновления

1. Зафиксировать версии приложения, PostgreSQL/SQLite и, при наличии,
   TimescaleDB. Снять количества строк, список ключей/индексов и контрольную
   выборку scores, метрик и объяснений. Сохранить конфигурации и модельный реестр
   отдельно от исходного кода; обеспечить защищённую копию ключей шифрования.
2. Остановить все писатели и процессы, которые могут впервые получить движок:
   web workers, scheduler, collectors, CLI/warmup. Не запускать старую и новую
   версии приложения одновременно. Окно обслуживания обязательно.
3. Снять согласованную резервную копию всей monitoring-БД, проверить checksum
   и восстановить её в **новую тестовую БД**. Продолжать только после проверки
   восстановления. Резервная копия должна оставаться неизменяемой.
4. Запустить новый код один раз на восстановленной копии, затем проверить
   сохранность строк, полные ключи, чтение legacy и двух новых версий одного
   наблюдения, кэш и удаление тестового проекта. Для PostgreSQL проверить
   параллельную инициализацию. Для TimescaleDB проверить реальные hypertables,
   chunks, индексы и ограничение уникальности с включённым временем.
5. При успешной репетиции один новый процесс выполняет инициализацию рабочей
   БД. Проверить те же инварианты до запуска остальных workers и писателей.
   PostgreSQL session advisory lock `730120260039` сериализует инспекцию и DDL
   новых процессов; он не останавливает старые процессы и произвольных писателей.
   SQLite требует единственного процесса миграции: блокировка в приложении
   не является межпроцессной блокировкой миграций.
6. Возобновить обслуживание, проверить collection, выбранную версию, объяснения,
   уведомления и журналы. Держать старую копию до завершения приёмки.

## Воспроизводимый backup/restore на отдельных базах

Следующие команды — процедура для оператора. Они не выполнялись на рабочей БД
при исправлении PR. Имена файлов/сервисов примерные; каталоги должны быть доступны
только владельцу. Секреты передавать через защищённые настройки libpq, не Git.

SQLite, после остановки писателей:

```bash
umask 077
sqlite3 /secure/monitor.db '.backup /secure/monitor-before.db'
sha256sum /secure/monitor-before.db > /secure/monitor-before.db.sha256
sha256sum --check /secure/monitor-before.db.sha256
cp /secure/monitor-before.db /secure/monitor-rehearsal.db
sqlite3 /secure/monitor-rehearsal.db 'PRAGMA integrity_check; PRAGMA foreign_key_check;'
DATABASE_URL=sqlite:// MONITOR_DB_URL=sqlite:////secure/monitor-rehearsal.db \
  python -c 'from app.metrics_storage import get_engine; get_engine()'
```

Ожидаются `ok` и отсутствие нарушений FK. Сверить counts/ключи до и после,
а не ограничиваться `integrity_check`. После репетиции снова снять backup,
если писатели с момента первой копии возобновлялись.

PostgreSQL: настроить libpq service `monitor_source` и пустую отдельную БД
`monitor_rehearsal` с совместимыми версиями. Выполнять от имени роли с нужными
правами; права/владельцы объектов также входят в проверку восстановления.

```bash
umask 077
PGSERVICE=monitor_source pg_dump --format=custom --file=/secure/monitor-before.dump
sha256sum /secure/monitor-before.dump > /secure/monitor-before.dump.sha256
sha256sum --check /secure/monitor-before.dump.sha256
pg_restore --list /secure/monitor-before.dump > /secure/monitor-before.contents
PGSERVICE=monitor_rehearsal pg_restore --exit-on-error /secure/monitor-before.dump
```

Архив включает всю БД: ограничение экспорта только родительской таблицей может
не захватить зависимые объекты. См. [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)
и [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html).

Для **TimescaleDB** сначала создать совместимое расширение в отдельной целевой БД,
выполнить `SELECT timescaledb_pre_restore()`, восстановить весь архив, затем
`SELECT timescaledb_post_restore()`. Не применять параллельный `pg_restore -j`.
Версии PostgreSQL и расширения должны соответствовать репетиции;
[официальный порядок](https://www.tigerdata.com/docs/deploy/self-hosted/backup-and-restore/logical-backup)
сверяется для используемых версий. Эти шаги не заменены тестом plain PostgreSQL.

## Откат

При любой ошибке остановить запуск остальных процессов. Не пытаться запускать
старый код на БД с новым многоверсионным ключом и не удалять «лишние» версии.
Сохранить копию текущей БД для расследования и новых данных. Восстановить
проверенный backup в **другую пустую БД**, сверить counts, ключи, выборки и права,
проверить старое приложение на этой копии. Только затем переключить DSN на неё
и возобновить писателей. Исходная и неудачно обновлённая БД остаются сохранёнными.

Backup до обновления не содержит последующих записей. Перед таким откатом
оператор должен согласовать потерю этого интервала либо подготовить отдельный
проверенный перенос новых данных; автоматический перенос/схлопывание версий
запрещён. Исправления PR не выполняли разрушительных миграций на реальных данных.

## Отдельная техническая задача перед эксплуатационным развёртыванием

**Версионированные миграции и репетиция восстановления на TimescaleDB.**

Сейчас миграция автоматически вызывается при первом `get_engine()` и состоит
из нескольких транзакций. Добавленная PostgreSQL-блокировка предотвращает гонку
между новыми workers, но не превращает весь upgrade в одну атомарную миграцию.
Нужно выделить явную команду миграции, журнал версий и preflight; web/scheduler
должны проверять совместимость схемы до обслуживания. Добавить межпроцессную
сериализацию SQLite, проверки остановки писателей, отказ при несовместимом
downgrade и воспроизводимую репетицию backup/restore для поддерживаемых версий
PostgreSQL/TimescaleDB, включая существующие chunks/сжатие и аварийный обрыв DDL.
Приёмка задачи: параллельный upgrade без DuplicateColumn/UniqueViolation,
сохранность всех версий, проверенный restart после частичного сбоя и восстановление
в отдельную БД без потери backup. До этой приёмки требуется описанное окно
обслуживания; рабочее развёртывание TimescaleDB остаётся ограничением.
