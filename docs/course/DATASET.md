# Датасет для оценки обнаружения инцидентов

Датасет реализует подготовительную задачу [#7](https://github.com/aleksandr-novikov/ai-integration-development/issues/7) для [согласованного кейса](CASE.md). Он содержит синтетические наблюдения трёх таблиц, истинные интервалы инцидентов и временные выборки. Качество модели измерено в [серии экспериментов #9](experiments/RESULTS.md): на test найдены 9/9 инцидентов, но FPR 13,27% превышает цель 10%. Автоматические проверки качества модели остаются задачей #10.

## Как воспроизвести

Из корня репозитория с Python 3.11+:

```bash
python -m scripts.generate_ml_dataset --output data/course
```

Для генерации нужны только стандартная библиотека Python и файлы репозитория. База данных, Flask, NIM и Telegram не используются. Непустая папка не перезаписывается; для нового запуска выберите другую папку. `data/course/` исключена из Git: храним генератор, протокол и [эталонный манифест](dataset-manifest.json), а CSV воспроизводим командой.

Параметры зафиксированы: seed 42, начало `2026-01-01T00:00:00+00:00`, шаг 15 минут, проект `course-benchmark`. Можно передать `--seed`, `--start` (обязательно UTC), `--train-ticks`, `--validation-ticks`, `--test-ticks`, `--interval-minutes`. Изменение параметров означает новую версию данных; не сравнивать такие запуски как эксперименты на одном датасете.

| Файл | Период UTC по умолчанию | Наблюдения | Назначение |
|---|---|---:|---|
| `train.csv` | 1 января 00:15 — 14 января 23:45 | 4 029 | Обучение scaler и модели, нормальный режим |
| `validation.csv` | 15 января 00:00 — 21 января 23:45 | 2 016 | Выбор гиперпараметров и порога |
| `test.csv` | 22 января 00:00 — 28 января 23:45 | 2 016 | Финальная оценка выбранной модели |
| `incidents.json` | validation и test | 18 инцидентов | Истинные интервалы, типы и параметры вмешательств |
| `manifest.json` | Весь набор | — | Версия, параметры, SHA-256 файлов и генератора |

Всего 8 061 наблюдение. В каждом из validation/test по 9 инцидентов: три типа на каждой из таблиц `users`, `orders`, `events`. Метрики таблиц различаются по масштабу; одно наблюдение относится к одному проекту и одной таблице.

`dataset_id` — SHA-256 канонического JSON манифеста без самого поля `dataset_id`. Манифест фиксирует версию Python, хеши двух исходных файлов генератора и каждого файла данных. Для точного повторения используйте тот же код, параметры и версию Python из манифеста. Два запуска в разных папках проверены на побайтовое совпадение; путь вывода и текущая дата на данные не влияют. При другой версии Python сравнивайте хеши CSV отдельно: версия среды входит в `dataset_id`.

## Происхождение данных и разметки

Построение базового ряда переиспользует `_row_count_at` и `TableProfile` из существующего `scripts/seed_metrics_db.py`: чистые функции вынесены в `scripts/synthetic_metrics.py`, а прежние импорты сохранены. Генератор дашборда продолжает работать с прежними профилями. Для оценки взяты отдельные параметры: плавный рост, небольшая недельная сезонность и шум; инциденты не подгоняются под предсказания Isolation Forest.

`row_count` — число строк в таблице. `null_rate` — синтетическая средняя по колонкам доля NULL на уровне таблицы, в диапазоне [0, 1]. Для этого набора не генерируются реальные строки и колонки: оба значения моделируются напрямую. Это соответствует четырём признакам текущего детектора, но не проверяет корректность SQL-коллектора.

Инциденты задаются до расчёта признаков, с отдельным воспроизводимым источником случайности:

- `null_spike`: кратковременное увеличение доли NULL на 0,12–0,30.
- `volume_jump`: кратковременный скачок числа строк в 1,3–1,7 раза и восстановление.
- `regime_change`: более длительный режим с повышением числа строк на 10% и доли NULL на 0,08, затем восстановление.

В `incidents.json` сохранены тип, объект, выборка, начало и конец с включёнными границами, номера тиков и параметры вмешательства. В CSV `is_anomaly` и `incident_id` ссылаются на эту разметку. В интервал включён **один первый тик восстановления**, поскольку его дельта ещё отражает инцидент. Такой тик является частью события при подсчёте recall и задержки; если политика разметки изменится, нужна новая версия набора.

## Временные границы и защита от утечки

Наблюдения разделяются по времени сразу для всех таблиц. Метка времени не встречается в двух выборках. Дельты вычисляются только относительно предыдущего наблюдения той же пары `(project_id, table_name)`. Первый тик каждой таблицы опускается: у него нет предыдущего значения.

На границах validation и test предыдущий уже наблюдавшийся тик сохраняется. Это соответствует непрерывному сбору метрик: например, для первой точки validation доступен последний снимок train. Дельта не сбрасывается в ноль и не вычисляется из будущих значений. Продление test не меняет train или validation — это отдельно проверяется тестом.

Обучающий набор содержит только нормальный режим. Это явное учебное предположение: в реальной истории для обучения могут находиться неизвестные инциденты. Стандартный эксплуатационный путь `anomaly_detector.train()` не используется для оценки на CSV, поскольку он сам загружает временное окно из БД и не гарантирует наше разделение.

`load_features()` выбирает только `row_count`, `null_rate`, `d_row_count`, `d_null_rate`. Метки, идентификаторы инцидентов, таблиц и времена не попадают в признаки. Отдельный scaler обучается для каждой таблицы исключительно на train:

```python
from pathlib import Path
from scripts.generate_ml_dataset import fit_training_scaler, load_features

dataset = Path("data/course")
scaler = fit_training_scaler(dataset, "events")
x_train = scaler.transform(load_features(dataset, "train", "events"))
x_validation = scaler.transform(load_features(dataset, "validation", "events"))
# Модель обучается на x_train. Параметры и порог выбираются по validation.
# Только после фиксации выбора:
x_test = scaler.transform(load_features(dataset, "test", "events"))
# Повторный fit/fit_transform на validation или test запрещён протоколом.
```

Для этого примера нужен scikit-learn из `requirements.txt`. В [серии #9](experiments/RESULTS.md) все пять конфигураций используют одни и те же файлы и `dataset_id`. На test оценивается только выбранный вариант; повторный подбор по test недопустим. Метрики считаются по определениям CASE.md: доля обнаруженных интервалов, ложные сигналы вне интервалов и задержка в циклах. Дополнительно можно сохранить precision/recall/F1 по точкам, явно отличая их от показателей по событиям.

## Валидация перед экспериментами

После генерации выполните:

```bash
python -m scripts.validate_ml_dataset --dataset data/course --report /tmp/course-validation.json
```

Продолжать обучение можно только при коде завершения 0. [Протокол валидации и два отчёта](validation/README.md) описывают проверки задачи #8, воспроизведение намеренно испорченной копии и действия при ошибке.

## Проверки и ограничения

```bash
python -m pytest tests/test_generate_ml_dataset.py tests/test_seed_metrics_db.py -q
```

Проверки покрывают воспроизводимость, изменение seed, границы выборок и событий, восстановление после инцидента, отсутствие утечки из будущего, раздельные ряды, обучение scaler только на train, физические диапазоны, защиту от перезаписи, чтение CSV и запуск без внешних зависимостей. Это проверки подготовки набора, а не результаты экспериментов качества модели.

Синтетический набор мал: по девять событий на validation/test, без реальных сбоев SQL, пропущенных тиков и нерегулярного расписания. Сценарии имеют общую структуру; высокая оценка здесь не доказывает качество на неизвестных реальных инцидентах. Абсолютный `row_count` растёт со временем: повышенная доля ложных срабатываний на позднем периоде может выявить слабость исходного набора признаков. Не менять разметку и test, чтобы скрыть такой результат; исследовать признаки и параметры на validation. Результаты первой серии приведены в [#9](experiments/RESULTS.md); проверки качества модели остаются задачей #10.
