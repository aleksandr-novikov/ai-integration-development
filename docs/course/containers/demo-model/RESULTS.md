## Воспроизводимость

Это четыре разных утверждения. Каждое проверяется отдельно.

| Утверждение | Статус | Доказательство |
|---|---|---|
| Данные train/test совпадают с историческими | Подтверждено | SHA-256 train и test совпали во всех повторах, на всех уровнях SIMD |
| Метрики качества на test совпадают | Подтверждено | Блок `test` совпадает с evaluation.json полностью: на `X86_V4`, `X86_V3` и `X86_V2` нет ни одного пересечения порога |
| Обучение воспроизводит модель | Подтверждено в текущем окружении | Модели, обученные на `X86_V4` и `X86_V3`, совпадают: среднее и масштаб scaler, `offset_`, признаки и все массивы 100 деревьев (604 сравнения). Модель, обученная на `X86_V3`, на `X86_V4` даёт исторический SHA score |
| Побайтово одинаковые score | Только при одинаковом уровне SIMD | `X86_V4` → `0667678…8346` (исторический). `X86_V3` и `X86_V2` → `210f256d…7324`. Точного совпадения с историческим SHA на любом оборудовании не заявляется |

**Причина расхождения SHA score.** Причина установлена экспериментально. Это
выбор вычислительных ядер NumPy во время работы (runtime CPU dispatch), а не
различие данных, модели или Python. Хост VDS2 поддерживает AVX-512
(`X86_V4`). Отключение этого уровня (`NPY_DISABLE_CPU_FEATURES=X86_V4`) даёт
`210f256d…`. Это же значение получено в предыдущем повторе; его окружение
и уровень SIMD не записаны. Различие появляется только в `decision_function`: отличаются 213 из
4 400 score, максимум |Δ| = 1.1e-16, смен знака нет. Ближайший к порогу score
равен 9.8e-5. Условия и прогоны —
в [scores-reference.json](scores-reference.json).

**Эталоны score.** Исторический SHA сохранён без изменений и остаётся эталоном
своего уровня `X86_V4`. Новый эталон добавлен только для `X86_V3` и `X86_V2`
(одно значение для обоих уровней). Выполнены условия:

- python 3.12, scikit-learn 1.6.1, numpy 2.5.4 и skops 0.16.0 записаны и
  сверяются при каждой проверке;
- уровень SIMD записывается в `environment.numpy_simd`;
- на каждом уровне два независимых обучения дали одинаковые score;
- исторический SHA и факт расхождения сохранены.

Что не проверено:

- хост без AVX-512 физически не проверялся: `X86_V3` и `X86_V2` получены
  отключением диспетчеризации на одном хосте;
- влияние `AVX512_ICL`/`AVX512_SPR` не проверено: на хосте этих расширений нет,
  такой хост сверяется с эталоном `X86_V4`;
- Python 3.12.16 этой доработкой не запускался: равенство score на 3.12.3 и
  3.12.16 взято из исходных данных задания.

**Проверка в CI.** Compose CI обучает и оценивает модель внутри образа. Хост
записывает в `demo_model_reproduced` (`ci-report.json`) четыре сравнения:

- SHA train и test — с evaluation.json;
- метрики test — с evaluation.json;
- SHA score — с эталоном того же окружения (python 3.12, scikit-learn, numpy,
  skops, `numpy_simd`).

`check-outcome` завершается ошибкой, если хотя бы одно сравнение не `true`, а
также если для окружения нет эталона. NumPy и SciPy в requirements не
закреплены. Поэтому новый выпуск NumPy остановит CI, пока для него не будет
создан эталон по тем же условиям. Заменять SHA результатом одного прогона
нельзя.

## Что это значит для CI и ограничения

- Один прогон Compose CI — одна случайная реализация нормального потока
  (`live_demo` не фиксирует зерно). По test вероятность успешного сценария
  ≈0.95 (0.91–0.97): примерно в одном прогоне из 20 возможна ложная тревога.
  При таком исходе `check-outcome` честно падает; порог, зерно и модель ради
  PASS не подбираются, нужен анализ отчёта.
- Данные синтетические. Точность симулятора относительно реальных INSERT и
  арифметики коллектора проверена тестом на SQLite
  (`tests/test_demo_model.py`); PostgreSQL-путь `n_live_tup` полагается на
  `pg_stat_force_next_flush()`, как и сам CI-сценарий.
- Первая офлайн-оценка по ошибке получила source с `table_name=orders`, из-за
  чего эталоном стала модель #9 для `orders`. Повтор с `events` дал те же SHA
  данных, score и метрики demo-модели; в файле — повтор. Других повторов test
  не было.
- Допуск реестра не выдаётся (`evaluation` в манифесте пустой): только
  `demo=true`, `quality_admitted=false`. Модель не предназначена для
  промышленного мониторинга; область применимости — 1–14 тыс. строк и 0–300
  строк за сбор.
