# Учебный кейс: обнаружение аномалий в метриках DB Monitoring (Isolation Forest)

## 1. Основа и границы учебного проекта

Итоговый проект по дисциплине «Интеграция искусственного интеллекта в разработку» выполняется на базе ранее разработанной системы **DB Monitoring**.

DB Monitoring — веб-система для мониторинга состояния и качества данных в базах данных. Система подключается к контролируемым БД, периодически собирает метрики, хранит их историю, визуализирует изменения и использует аналитические и ML-механизмы для выявления отклонений.

В рамках новой дисциплины команда не разрабатывает DB Monitoring заново. Существующий проект используется как техническая основа, а учебная работа направлена на прохождение полного жизненного цикла выбранного ИИ-компонента:

**задача → архитектура → данные → эксперименты → тестирование → сервис → развёртывание → мониторинг → сопровождение модели.**

## 2. Пользователь

Основной пользователь системы — специалист, отвечающий за качество и эксплуатацию данных, например дата-инженер, аналитик данных или другой сотрудник команды данных.

Пользователю необходимо своевременно понимать, что поведение данных стало нетипичным и требуется ручная проверка.

Система помогает обнаружить потенциальный инцидент, но не исправляет данные автоматически и не принимает окончательное решение вместо специалиста.

## 3. Бизнес-задача

При эксплуатации информационных систем могут возникать нарушения качества данных, которые не приводят к техническому отказу базы данных.

Например, может резко увеличиться доля пропущенных значений, нетипично измениться объём данных или нарушиться привычная динамика показателей. Такие отклонения способны оставаться незамеченными до тех пор, пока некорректные данные не попадут в отчётность, аналитику или другие зависимые процессы.

Задача проекта — сократить время обнаружения подобных инцидентов за счёт автоматического анализа истории показателей мониторинга и выделения состояний, требующих внимания специалиста.

## 4. Основной ИИ-кейс

Основной ИИ-кейс учебного проекта — **обнаружение аномалий в показателях мониторинга данных с использованием Isolation Forest**.

Isolation Forest — метод обнаружения аномалий без учителя. Он позволяет искать нетипичные наблюдения без необходимости заранее описывать отдельные правила для каждого возможного инцидента. Результат модели рассматривается как сигнал для последующей проверки человеком, а не как окончательное доказательство наличия ошибки в данных.

**Что уже есть и что делается в рамках курса.** Оценка аномальности на основе Isolation Forest уже присутствует в исходном DB Monitoring и относится к унаследованной части проекта. Учебная работа не создаёт детектор с нуля, а превращает его в воспроизводимый и проверяемый ИИ-компонент: датасет с известными инцидентами и временным разбиением, оценка по критериям из раздела 7, серия экспериментов в MLflow, валидация данных, тестирование, контракт сервиса, воспроизводимый запуск, мониторинг и стратегия работы с дрейфом. Способ формирования обучающей выборки и использование размеченных инцидентов будут зафиксированы при подготовке датасета и протокола экспериментов.

Остальные аналитические механизмы DB Monitoring (прогноз, PSI/KS, поиск точек изменения, контроль схемы) и LLM-объяснения сигналов не являются предметом основного кейса. Они рассматриваются как контекст системы или элементы мониторинга. Ограничения LLM-объяснений оцениваются отдельной задачей плана (#18).

## 5. Входные данные и метрики

Источником данных для модели является история метрик, собираемых DB Monitoring.

В исходной версии DB Monitoring компонент Isolation Forest использует четыре признака:

- количество строк в таблице (`row_count`);
- доля пропущенных значений (`null_rate`);
- изменение количества строк между соседними наблюдениями (`d_row_count`);
- изменение доли пропущенных значений между соседними наблюдениями (`d_null_rate`).

Перед обучением признаки масштабируются с помощью `StandardScaler`. В базовом коммите `1a869e4` модель обучается на истории за 60 дней с параметрами `n_estimators=100`, `contamination=0.01`, `random_state=42`.

Эта конфигурация относится к унаследованной части DB Monitoring и не считается результатом новой дисциплины. В рамках учебного проекта набор признаков и параметры модели планируется повторно исследовать в серии воспроизводимых экспериментов; по их результатам исходная конфигурация может быть подтверждена или изменена. Все изменения должны быть зафиксированы в материалах экспериментов.

Одно наблюдение — снимок метрик одного объекта мониторинга (таблицы; если `null_rate` считается по колонкам — таблицы и колонки) в момент цикла сбора. Уровень агрегации `null_rate` уточняется при подготовке датасета.

Инциденты для оценки качества могут быть внесены в историю метрик искусственно (в том числе сценариями демонстрационного генератора `live_demo`) и/или размечены вручную. Происхождение данных указывается в описании датасета и учитывается как ограничение проекта.

## 6. Результат работы системы

Для анализируемого наблюдения система должна формировать результат, позволяющий специалисту определить необходимость дальнейшей проверки.

Результат включает:

- таблицу или другой объект мониторинга;
- время наблюдения;
- значения использованных входных признаков;
- признак нормального или аномального состояния;
- числовую оценку аномальности модели.

Результат может использоваться в интерфейсе DB Monitoring, через API и в механизмах уведомления.

## 7. Измеримые критерии успеха

Для проверки качества модели используется воспроизводимый тестовый набор с известными инцидентами. Данные для обучения и оценки разделяются по времени: оценка выполняется на более позднем периоде, чем обучение и подбор порога.

**Определения**

- Наблюдение — снимок метрик одного объекта мониторинга в момент цикла сбора.
- Инцидент — размеченный интервал [`t_start`, `t_end`] на объекте мониторинга; `t_start` — первое наблюдение с отклонением.
- Сигнал — наблюдение, которое модель классифицировала как аномальное согласно заранее зафиксированному порогу. Порог выбирается до оценки качества на тестовом периоде.
- Инцидент считается обнаруженным, если на том же объекте есть хотя бы один сигнал в интервале [`t_start`, `t_end`].
- Задержка обнаружения — число циклов сбора от `t_start` до первого сигнала в обнаруженном инциденте.

### 7.1. Полнота обнаружения инцидентов

Целевой показатель — обнаружение **не менее 80 % размеченных инцидентов**. Число инцидентов в тестовом наборе указывается вместе с результатом.

### 7.2. Ложные срабатывания

Целевой показатель — **не более 10 % наблюдений вне интервалов инцидентов**, которые модель помечает как аномальные (число ложных сигналов / число наблюдений вне интервалов инцидентов).

### 7.3. Задержка обнаружения

Целевой показатель — **медианная задержка обнаружения не более одного цикла сбора метрик**.

При стандартной настройке DB Monitoring один цикл сбора составляет 15 минут. Критерий применим к инцидентам с резким началом (скачок объёма, доли пропусков); для медленных изменений момент начала определяется при разметке датасета.

Указанные значения являются целевыми критериями, выбранными командой для учебного проекта, а не уже достигнутыми результатами. Фактические показатели будут рассчитаны в ходе экспериментов по единой процедуре расчёта. Если результаты покажут необходимость изменения порогов, это должно быть отдельно обосновано и отражено в итоговых материалах проекта.

## 8. Что унаследовано от DB Monitoring

В качестве технической основы используются возможности, реализованные в DB Monitoring до начала дисциплины, в том числе:

- сбор и хранение истории метрик, планировщик периодических задач, отдельное хранилище метрик;
- работа с несколькими СУБД;
- Flask-приложение, веб-интерфейс с дашбордами и REST API;
- оценка аномальности на основе Isolation Forest (оценки аномальности сохраняются в хранилище метрик);
- прогнозирование роста таблиц;
- анализ дрейфа распределений (PSI, KS-тест);
- поиск точек изменения;
- контроль изменений схемы;
- LLM-объяснения сигналов и уведомления;
- Docker-контейнеризация и Docker Compose;
- unit-, интеграционные и E2E-тесты, CI;
- технический мониторинг и журналирование (Prometheus-метрики, Sentry, структурированные логи, health-check, feature flags);
- механизмы выпуска и отката версий Docker-образов, резервное копирование и runbooks.

Эти возможности являются унаследованной частью проекта. Их наличие само по себе не означает, что задания курса выполнены: для каждой задачи курса нужен отдельный проверяемый результат. В частности, наличие Isolation Forest в исходном проекте не считается результатом учебной работы.
