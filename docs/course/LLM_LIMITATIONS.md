## Назначение и границы достоверности

Isolation Forest обнаруживает статистическое отклонение. LLM предлагает **гипотезу о возможной причине**, а не установленную причину инцидента. Скачок `row_count` сам по себе не доказывает удаление данных или сбой ETL. Журналы ETL, история SQL, ручные действия, плановые удаления и внешние события в этом контексте отсутствуют. Проверка JSON не является проверкой истинности текста.

`confidence` — число, предоставленное моделью либо заданное правилами; калибровки по размеченным причинам нет. `0.85` не означает доказанную вероятность правильности 85%. UI показывает число в процентах. В промпте есть категоричное `CONFIRMED this point is an anomaly`, даже когда score отсутствует: endpoint не проверяет, что `ts` действительно является аномалией. Это может усиливать ложную уверенность. **Подтверждено кодом**, семантический пробел **воспроизведён тестом** с неподтверждённой причиной и `confidence=0.99`.

## Фактический путь запроса

Источники: [app.py: create_app](../../app/app.py), [projects.py: load_current_project_into_g](../../app/projects.py), [api.py: explain](../../app/api.py), [llm.py](../../app/llm.py), [metrics_storage.py](../../app/metrics_storage.py).

1. `POST /api/explain`: глобальный hook для авторизованного пользователя выбирает `g.current_project` из доступных ему проектов по сессии либо первый доступный. Для анонимного пользователя текущего проекта нет. Login gate защищает HTML-префиксы, общей обязательной авторизации `/api` нет; API освобождён от CSRF. Валидация `table/metric/ts` проверяет непустоту строк и разрешает только `row_count/null_rate`; формат времени, типы JSON и факт аномалии полноценно не проверяются.
2. **Сразу читается общий кэш**, ещё до вызова `_current_project_id()` и `_has_project_table_metrics()`. Cache hit возвращается пользователю. Ключ `(table_name, metric, ts)`, TTL 24 часа от `created_at`; ни `project_id`, ни подключение в ключе не участвуют. Истёкшая запись не выдаётся, физически здесь не удаляется.
3. На cache miss `_current_project_id()` берёт `g.current_project['id']` либо `legacy`. `_has_project_table_metrics()` ищет последнюю `row_count` или scores за 14 дней в этом проекте; при отсутствии — 404. Это проверка наличия данных таблицы, а не отдельное доказательство доступа к конкретной аномалии/подключению.
4. `explain_anomaly()` без ключа сразу вызывает правила, без подготовки промпта. С ключом `_build_prompt()` читает метрики, change-points и scores с `project_id`. **Схема читается через `get_schema_snapshot(table)` без передачи проекта**, следовательно из `legacy`. Это отдельный открытый дефект изоляции.
5. Контекст включает обе метрики. Окно запроса — минимум 48 часов, расширяется до возраста `ts` + 2 часа. Метрики отсекаются строковым сравнением `r['ts'] <= ts`, отправляются последние 10 точек и статистики всей выбранной истории. Change-points запрашиваются минимум за 14 дней, но не отсекаются по `ts`; возможен контекст событий после аномалии. Надписи «48 h»/«14 days» могут не соответствовать расширенному окну. Это **обнаружено статически**, универсальная корректность времени не проверена.
6. `_call_nim()` синхронно вызывает настроенный `NIM_BASE_URL/chat/completions`: одно сообщение роли `user`, `temperature=0.2`, `max_tokens=512`, тайм-аут HTTPX 60 секунд. Настройка по умолчанию — NVIDIA NIM, `meta/llama-3.3-70b-instruct`; фактический production deployment не проверялся. Сетевые `RequestError`, включая timeout, повторяются до 3 попыток с ожиданиями 2/4 секунды. HTTP-ошибки 4xx/5xx не повторяются. Это не общий deadline 60 секунд на весь запрос.
7. Из `choices[0].message.content` извлекается текст. `_parse_nim_response()` снимает Markdown fences, пробует JSON и извлечение объекта из текста; непустое `explanation` приводится к строке. `suggested_fix` может отсутствовать. `confidence` преобразуется в float и ограничивается диапазоном; ошибка преобразования даёт 0.5. Строгой схемы типов и проверки фактов нет.
8. Пустой/неразбираемый ответ или исключение внутри NIM-пути приводит к `_rule_based_explain()`, `confidence=0.3`: резкое падение/рост строк, высокий NULL либо общий запрос ручной проверки. Ошибки чтения хранилища внутри самих правил могут выйти наружу: docstring «Never raises» не является гарантией доступности БД.
9. API сохраняет результат (в том числе fallback) через `save_explanation()` в общий кэш с новым `created_at`, возвращает JSON. При восстановлении NIM fallback может оставаться в кэше до 24 часов. Ошибки чтения/записи кэша API не перехватывает. Признак происхождения «NIM/правила», версия модели/промпта и доказательства причины в кэше отсутствуют.
10. [table_detail.html: fill](../../templates/table_detail.html) выводит `explanation` и `suggested_fix` через `textContent`, число — полосой/процентом; текст не становится HTML. Подтверждено статически. Визуальная браузерная проверка не проводилась. [Telegram: notify_anomaly](../../app/notifications/telegram.py) при включённом флаге вызывает объяснение напрямую, минуя API-кэш, и отправляет текст объяснения; эвристика `confidence > 0.3` не доказывает происхождение или качество ответа.

**Безопасный целевой порядок для #12:** установить пользователя/проект и разрешённый источник → проверить доступ к таблице → читать кэш с полной идентичностью → готовить разрешённый контекст → модель/правила → проверка → сохранение/ответ. Этот порядок **планируется**, а не реализован данным PR.

## Данные и граница доверия

| Категория | Что реально передаётся в NIM |
|---|---|
| Идентичность и схема | Название таблицы; имена, типы и nullable колонок из schema snapshot (сейчас ошибочно `legacy`) |
| Время и метрики | Время аномалии, trigger metric, до 10 значений каждой `row_count/null_rate` с временем; min/max/median, число наблюдений, отношение/дельта к медиане |
| Детекция | Score аномалии в заданный момент; время, имя метрики и значения до/после change-points |
| Служебные поля запроса | Имя модели, параметры генерации; синтетический/настоящий API key используется только в Authorization, не в промпте |

`project_id` используется для части локальных чтений, но непосредственно в промпт не вставляется. Содержимое строк исходной БД, значения ячеек, исходные SQL, DSN/пароли подключения, пользователи/права, токены Telegram и ETL-логи в этом пути в промпт не добавляются. Это **подтверждено кодом конкретного пути**, не утверждение о полной обезличенности: чувствительные сведения могут оказаться уже в именах/типах. Статистики и временные паттерны также могут раскрывать информацию о деятельности.

Имена таблицы/колонок/типов и change-point metric интерполируются в одно `user`-сообщение. Нет отдельной границы «инструкции / недоверенные данные», нейтрализации инструкций, allowlist метаданных или ограничения их длины. Проверка обязательных API-параметров и SQL bind parameters не защищают LLM от prompt injection. Тест с безопасным `SYNTHETIC_MARKER` подтверждает дословное попадание внедрённых инструкций в HTTP payload, сохранение и возврат текста с HTML-подобной разметкой. Ответ в тесте задан MockTransport: **следование настоящей модели внедрённым инструкциям не проверено**. SQL в `suggested_fix` остаётся текстом.

Перед реальными данными нужны согласование внешней обработки, классификация/минимизация метаданных, псевдонимы имён, проверка endpoint/условий хранения и журналирования провайдера, контроль доступа к контексту и тесты инъекций. Эти меры **планируются**. В аудите реальные корпоративные данные и секреты не использовались; реальных запросов в NIM не было.

## Межпроектный кэш: воспроизведение и передача в #12

Временная SQLite, два разных пользователя и два проекта A/B без общего членства, раздельные аутентифицированные сессии Flask-Login. Сессии создаются тестом; password login flow не является предметом этого сценария. `LOGIN_DISABLED=False`, реальный hook выбора проекта, реальный API, SQL-хранилище и кэш; подменён только ответ NIM. Таблица `orders`, `row_count`, один timestamp. У A есть метрики; у B в одном варианте есть одноимённая таблица, в другом нет.

Запрос A сохраняет `project-A-only`. Следующий запрос B с тем же ключом получает **200 и объяснение A**; собственная генерация B не выполняется. Без таблицы B также получает 200 вместо ожидаемого 404. Проверка доступа после cache hit не достигается. Это **воспроизведённая утечка**, а не только замечание старого ревью. Существующие [тесты изоляции метрик](../../tests/test_tenant_isolation.py) проходят, но не закрывают общий кэш объяснений.

Ключ одинаков в [SQLite](../../scripts/metrics_schema.sql) и [PostgreSQL/Timescale](../../scripts/timescale_schema.sql); `save_explanation/get_cached_explanation` не принимают проект. В PostgreSQL проблема пока **обнаружена статически**, воспроизведение на сервере не выполнялось.

[Открытая #12](https://github.com/aleksandr-novikov/ai-integration-development/issues/12) уже содержит этот риск и требование регрессии. Данный PR передаёт ей сценарии и следующие требования, не меняя авторизацию/схемы:

- Проверять доступ **до** кэша; включить `project_id`, идентичность подключения/схемы/таблицы и согласованное время в чтение, запись, unique/primary key и upsert. Одного `project_id` мало для совпадающих таблиц разных подключений внутри проекта; уточнить контракт в [#4](https://github.com/aleksandr-novikov/ai-integration-development/issues/4).
- Согласованно обновить SQLite/PostgreSQL DDL, миграции существующих БД, API/helpers и [перенос в Timescale](../../scripts/migrate_metrics_to_timescale.py). Старые объяснения не содержат доказанного владельца: не назначать их произвольному проекту; изолировать/инвалидировать или пересоздать по явной политике.
- Передавать проект при чтении schema snapshot; отдельно проверить идентичность подключения во всём контексте. Добавить испытания обновления старой БД, истечения TTL, одинаковых ключей, отказа доступа и повторной записи для обоих backend.

Три безопасных контракта оставлены как `xfail(strict=True, raises=AssertionError)` с причинами #12/#18. Они **выполняются**, обычный CI с `pytest -v` показывает XFAIL; неожиданное прохождение станет XPASS(strict) и провалит CI, требуя снять маркер после исправления. Технические ошибки не маскируются `raises=AssertionError`; ошибки подготовки A дополнительно превращены в RuntimeError. Это явный учёт открытых дефектов вне миграционного объёма #18. Отдельный запуск `--runxfail` ниже показывает реальные FAIL. Изоляция не объявляется успешно защищённой.

## Ответственность человека и последующие улучшения

**Подтверждено кодом:** потребители `suggested_fix` — JSON API, параметризованная запись кэша и `textContent` UI; пути исполнения рекомендации как SQL/команды не найдено. Telegram отправляет объяснение, а не применяет исправления. ИИ не предоставлено самостоятельное право менять БД или принимать эксплуатационные решения. Ночное ML-обучение и обычные фоновые операции приложения не являются выполнением LLM-рекомендаций.

Человек проверяет гипотезу по исходным метрикам, ETL/SQL-журналам и плановым изменениям, выбирает действие и отвечает за его применение. Текущий интерфейс не обеспечивает обязательное подтверждение фактов; сохранённый текст также остаётся недоверенным.

План улучшений: [#12](https://github.com/aleksandr-novikov/ai-integration-development/issues/12) — изоляция/порядок доступа/схема контекста; [#4](https://github.com/aleksandr-novikov/ai-integration-development/issues/4) — типы/время/ошибки и идентичность источника; [#11](https://github.com/aleksandr-novikov/ai-integration-development/issues/11) — включить эти проверки в общую стратегию. При продолжении Responsible AI-работ по [#18](https://github.com/aleksandr-novikov/ai-integration-development/issues/18) или отдельной согласованной задаче нужны строгая схема результата с конечным числом confidence, маркировка «гипотеза» и «NIM/правила», версия модели/промпта, минимизация контекста, разделение инструкций/данных и семантические проверки на размеченных причинах. Эти меры сейчас **планируются**; новая Issue этим аудитом не создавалась. Один только иной текст промпта не гарантирует защиту от injection/галлюцинаций.

В системном Python изначально не было pip/pytest; создан `/tmp/issue18-venv`, установлены необходимые зависимости из требований проекта (без полного ML/Docker-окружения). Для итогового запуска Pydantic/core приведены к 2.13.2/2.46.2.
