# Контракт ML API — задача #4

**Два документа описывают разные состояния системы.**

| Спецификация | Что описывает | Статус |
|---|---|---|
| [legacy.openapi.yaml](legacy.openapi.yaml) | `GET /api/anomalies/{table_name}`, `GET /api/forecast/{table_name}` | Существующий Flask API, база `a1c814d` |
| [inference.openapi.yaml](inference.openapi.yaml) | `POST /v1/predict` | Проект внутреннего API по [ADR-001](../../adr/001-flask-and-inference-service.md); реализуется в #12 |

Для ДЗ В03 предназначен `inference.openapi.yaml`: один endpoint, OpenAPI 3.1.0,
типы/ограничения, авторизация, примеры, успешный ответ и ошибки. Второй документ
фиксирует фактическое поведение приложения и позволяет проверять его по HTTP.
Наличие YAML и успешные проверки схемы не означают, что FastAPI уже реализован.
Три endpoint и проверка через Swagger UI по В09 остаются в #12.

## Существующий API

```bash
curl 'http://localhost:5001/api/anomalies/orders?range=7d'
curl 'http://localhost:5001/api/forecast/orders?metric=row_count&horizon=1d'
```

Первый запрос возвращает сохранённые scores; обучение не запускается. Ответ
`200 []` не различает неизвестную таблицу, пустую историю и отсутствие scores.
Если сохранённые scores есть, отсутствие joblib не препятствует их чтению;
дополнительный `features` может отсутствовать. `is_anomaly` здесь — **0 или 1**.

Второй запрос требует `FF_FORECAST=true`; при выключенном флаге всегда HTML 404,
в том числе при неправильных параметрах. При включённом флаге: недопустимые
metric/horizon → JSON 400; недостаточно истории → JSON 422 с
`error: insufficient_data` и `message`. Нет сохранённой модели, но есть история →
возможно обучение в запросе. Оно также запускается, если `last_ts` модели
отстаёт от последней точки истории больше чем на час или изменился последний
changepoint. Свежая модель с тем же changepoint используется повторно.
Технические исключения могут дать HTML 500.
Прогноз строится для `row_count`/`size_bytes`, не для `null_rate`.

Существующая сессия Flask-Login определяет текущий доступный проект. Без неё
используется `legacy`; общей обязательной авторизации этих маршрутов сейчас нет.
`?project_id=...` не выбирает проект, а bearer-токен нового контракта здесь не
реализован. Не обещаем 401/403, которых текущий код не возвращает. У legacy scores
нет версии модели и идентичности подключения/схемы; эти ограничения не исправлены
спецификацией. Детали — [архитектурная сверка](../architecture-review.md).

## Проект инференса: вход и источник

Flask-адаптер сначала проверяет пользователя, членство в проекте и доступ к
подключению. Он читает только разрешённые данные и формирует четыре
немасштабированных признака. FastAPI проверяет сервисный токен и разрешённый
источник, загружает опубликованную модель/scaler и предсказывает **без fit**.

| Поле | Значение и правило |
|---|---|
| `source.project_id` | ID проекта; не произвольный способ переключить права |
| `source.connection_id` | ID подключения внутри этого проекта, не DSN и не имя БД |
| `source.schema_name` | Схема; для Iceberg — полный effective namespace |
| `source.table_name` | Имя таблицы; сравнивается точно с остальными полями источника |
| `observed_at` / `previous_observed_at` | RFC 3339 с часовым поясом; предыдущая точка строго раньше текущей |
| `model_version` | Неизменяемый ID опубликованного манифеста #5, не путь к файлу |
| `feature_schema_version` | Версия построения признаков; в первом контракте поддерживается `1.0.0` |
| `features` | `row_count >= 0`, `null_rate` в [0, 1], `d_row_count`, `d_null_rate` в [-1, 1]; только конечные JSON-числа |

`project_id` и `connection_id` — непустые ASCII ID длиной до 128 символов:
буква/цифра в начале, затем буквы, цифры, `.`, `_`, `:`, `-`. Имена схем и таблиц
длиной 1–255 символов сохраняются точно, включая регистр и допустимые для БД
пробелы; их нельзя автоматически обрезать или приводить к нижнему регистру.
Версия схемы — три целых компонента без ведущих нулей, всего до 32 символов.

Равенство имён таблиц не означает равенства источников. Идентичность для новых
scores в #12: **`(project_id, connection_id, schema_name, table_name, ts,
model_version, feature_schema_version)`**, где `ts` — нормализованный UTC
`observed_at`. Ключ/upsert, чтение API/дашборда и миграции должны использовать
одинаковую идентичность. Повтор того же входа по полному ключу идемпотентен; другая версия
сохраняется отдельно. Текущая история не содержит достаточных данных для
восстановления подключения: нельзя приписывать её случайному `connection_id`.
Политика сохранения legacy-строк и миграция — #12. При переименовании схемы или
таблицы возникает новый source; автоматическое объединение истории не обещается.

До подключения нового адаптера #12 должна обеспечить эту идентичность и при
сборе/чтении исходных метрик и снимков схемы. Добавить connection_id только в
ответ или таблицу scores недостаточно: текущая история по проекту/имени таблицы
может уже смешивать подключения. Если источник старых наблюдений нельзя доказать,
адаптер отказывает с 409 `ambiguous_source`, не угадывает владельца и не вызывает
инференс. Это будущий ответ адаптера; миграция истории не выполняется в #4.

Сервисная аутентификация — `Authorization: Bearer <opaque-token>`. Principal
токена связан в конфигурации сервиса с allowlist полных источников. Сначала
проверяется токен, затем доступ к source, затем модель; тело запроса не расширяет
права. Сервис не обращается к БД истории. Пользовательская авторизация остаётся
во Flask, токен не передаётся в браузер, URL или логи. Вне изолированного
локального стенда нужен TLS. Реализация и тесты отказов доступа — #12.

## Признаки и отсутствие истории

Порядок для scaler/IF: `[row_count, null_rate, d_row_count, d_null_rate]`.
`null_rate` — средняя доля NULL по колонкам таблицы, как в существующем контуре.
Точки `row_count` и `null_rate` сначала совмещаются по времени. Дельты считаются
между текущим и предыдущим **доступным согласованным** наблюдением, без деления
на длительность разрыва. Например, 100 → 110 через час даёт `d_row_count=10`.
Несовпавшие timestamps не заполняются нулями.

Если предыдущей согласованной точки нет, адаптер не вызывает `/v1/predict`,
а сообщает своему клиенту 422 `insufficient_history`. Это будущая ошибка
адаптера, не новый ответ существующего Flask API и не результат текущего YAML.
Некорректное поле `previous_observed_at` в запросе инференса — 422 `invalid_input`.
Межполевые проверки: `previous_observed_at < observed_at`,
`row_count - d_row_count >= 0`, `null_rate - d_null_rate` в [0, 1]. Их реализация
в #12 обязательна: JSON Schema не сравнивает поля между собой.

В #5/#12 общая чистая функция должна использоваться и обучением, и адаптером;
FastAPI дельты повторно не вычисляет и использует только scaler выбранного
артефакта. Сейчас тест сверяет пример с реальным `_load_features`, включая
пропуски и разрыв времени; работающего online-адаптера для сквозного теста ещё нет.

## Примеры и ошибки будущего сервиса

Полные примеры находятся непосредственно в YAML и проверяются тестами.
`demo-if-2026-09-26`, `score=-0.12` и source в примерах — **синтетические значения
контракта**, не результат нового эксперимента и не опубликованная рабочая модель.
Baseline #9 с FPR 13,27% не получает положительного допуска. Её отдельная учебная
демонстрация провала качества должна быть явно обозначена по ADR-001.

| HTTP | Код `error.code` | Ситуация |
|---|---|---|
| 400 | `invalid_json` | JSON не разбирается, включая NaN/Infinity |
| 401 | `authentication_required` | Нет действительного токена; заголовок `WWW-Authenticate: Bearer` |
| 403 | `source_forbidden` | Источник не разрешён principal токена |
| 409 | `feature_schema_mismatch` | Неподдерживаемая версия схемы или несовместимость с моделью |
| 415 | `unsupported_media_type` | Передан не `application/json` |
| 422 | `invalid_input` | Неправильные типы, диапазоны, даты или противоречивые признаки |
| 503 | `model_unavailable` | Нет указанной опубликованной модели/scaler либо нарушена целостность |
| 500 | `internal_error` | Техническая ошибка без секретов и traceback в ответе |

Успешный ответ содержит source, время, фактические версии модели/схемы,
сырой `score`, `threshold=0` и **boolean** `is_anomaly = (score < 0)`.
Сервис фиксирует одну пару модель/scaler на запрос и не подменяет отсутствующую
модель последним joblib. При нескольких ошибках одновременно действует
порядок `x-validation-order` из YAML:

1. Токен (401), Content-Type/строгий JSON (415/400), структура и типы (422).
2. Доступ к полному source (403), поддержка версии схемы сервисом (409),
   межполевые правила (422). На этих этапах артефакт ещё не читается.
3. Поиск `model_version` только для разрешённого source и проверка целостности
   манифеста (503). Версия другого источника считается отсутствующей и также
   даёт 503; существование чужой модели не раскрывается.
4. Сверка схемы запроса с целостным манифестом (409), затем наличие,
   целостность и десериализация модели/scaler (503).

Таким образом, повреждённый манифест даёт 503; несовместимая схема из целостного
манифеста — 409 до загрузки модели. Универсального приоритета 409 над 503 нет.

Числовая политика `x-json-policy` обязательна для реализации #12: строгий
декодер отклоняет `NaN`, `Infinity`, `-Infinity` и числа с переполнением binary64
(например, `1e400`) с 400. Строка `"110"` и boolean вместо числа дают 422 без
автоприведения. Все признаки и score должны быть конечными. `format: double`
и расширения `x-*` сами по себе этого не обеспечивают в произвольном валидаторе.
Тесты проверяют эталонную политику декодирования и схему с проверкой конечности;
это не HTTP-проверка будущего сервера. В #12 нужны такие же проверки на реальном
запросе и ответе, включая Pydantic без приведения строк/boolean к числам.

## Согласование с аудитом `/api/explain` (#18)

`POST /api/explain` не входит в эти две спецификации. Его существующие дефекты
воспроизведены в [аудите #18](../LLM_LIMITATIONS.md), исправления остаются в #12.
Для него согласованы следующие требования: авторизация пользователя и полного
источника **до чтения кэша**, ключ с проектом/подключением/схемой/таблицей,
метрикой и нормализованным временем; контекст только из разрешённого источника
как в API, так и в LLM-ветке Telegram. Чужой и анонимный клиент не получают
кэшированный ответ; порядок заполнения кэша не позволяет подменить результат
другого источника.

Числовое `table` и JSON-массив вместо объекта должны дать контролируемый 400,
а не нынешний 500. SQLite и PostgreSQL требуют согласованных миграций, upsert,
TTL и проверок повторного чтения; старые записи без владельца нужно изолировать
или инвалидировать по явной политике. Это требования будущей реализации,
а не уже работающие гарантии. Три строгих XFAIL аудита остаются открыты до #12.

## Версии и совместимость

`info.version=1.0.0` — версия этого описания, `/v1/` — MAJOR интерфейса будущего
API. Legacy-маршруты остаются без `/v1/`. `model_version`, версия данных в манифесте
и `feature_schema_version` имеют отдельный смысл и не выводятся друг из друга.

- **MAJOR:** переименовать обязательное `score` в `anomaly_score`, поменять знак
  score/смысл порога или потребовать новый обязательный признак. Нужен `/v2/`;
  изменение признаков также меняет feature schema и требует совместимого артефакта.
- **MINOR:** добавить необязательное поле `processing_ms` в успешный ответ.
  Это относится к верхнему уровню `PredictionResponse`, где разрешены новые
  поля; обязательные поля сохраняются. Вложенный `source` и объект ошибки
  строгие (`additionalProperties: false`): добавление полей туда нарушит
  текущий контракт и потребует MAJOR либо отдельно согласованной миграции.
- Новая опубликованная модель с той же схемой и семантикой ответа меняет
  `model_version`, сохраняя `/v1/`. Порог качества проверяется отдельно от HTTP.

Конкретный сценарий нарушения: разработчик переименовал `score`, дашборд читает
старое поле и перестаёт показывать оценку. Contract-test требует `score` и
отклоняет такой ответ до пользователей. Добавление `processing_ms` тот же тест
пропускает. Для уже существующих маршрутов тесты проверяют реальные HTTP-ответы;
для будущего `/v1/predict` пока проверяются схема и примеры, не реализация.
Схема также отклоняет несоответствие `is_anomaly` знаку `score`, включая
нулевую границу, и связывает каждый `error.code` с его HTTP-статусом.

## Целевой SLA и измерение

Это **предлагаемые цели**, фактические latency/доступность пока не измерены.
Учебный профиль: один worker, 2 vCPU/4 GiB, локальная сеть, прогретая модель,
одна таблица, один запрос/с; целевая доступность не задана без периода наблюдения.

| Операция | Предлагаемая цель p95 | Границы измерения |
|---|---|---|
| Legacy anomalies | ≤500 мс | До 672 сохранённых точек, без холодной загрузки артефакта |
| Legacy forecast | ≤2 с | Прогретая линейная модель, 10 точек истории, horizon=1d; не Prophet/обучение |
| Будущий predict | ≤100 мс | Один вход из четырёх признаков, уже загруженная модель/scaler; без чтения истории |

В #12/#13 записать CPU/RAM, версии, объём истории, прогрев и число запросов;
собрать не менее 100 успешных `curl -w '%{time_total}'` запросов, считать p95
методом ближайшего ранга. Отдельно фиксировать 4xx/5xx, таймауты и холодные
запуски; не исключать ошибки из отчёта. Время Flask-адаптера с чтением истории
измеряется отдельно от чистого инференса. Текущие contract-tests не доказывают SLA.

## Проверка

Из корня репозитория после установки `requirements-dev.txt`:

```bash
python -m openapi_spec_validator docs/course/api/legacy.openapi.yaml
python -m openapi_spec_validator docs/course/api/inference.openapi.yaml
python -m pytest -q tests/test_openapi_contract.py
```

Автоматический валидатор проверяет OpenAPI, тесты — примеры, обязательные поля,
диапазоны, версии, формат даты и фактические ответы существующего приложения.
Новый тест входит в обычный pytest и существующий CI без отдельного workflow.
Дополнительно можно открыть YAML в [Swagger Editor](https://editor.swagger.io/).
Проверка в Swagger Editor вручную здесь не заявляется.

Результаты локальной проверки после исправлений ревью приведены в
[verification.json](verification.json): оба валидатора, контрактный файл,
регрессии API/прогноза/детектора/изоляции и LLM-аудит; Ruff и `pip check`.
Итог: **189 passed, 3 xfailed**. XFAIL — известные дефекты #18, переданные в #12.
В тестах детектора сохранены предупреждения joblib о NumPy 2.5, они не скрыты.
Использовано отдельное Python 3.12-окружение с зависимостями проверяемого контура;
полный набор course/MLflow/Prophet, Docker и внешние сервисы не запускались.
Команды, версии и хеши проверенных файлов — [verification.json](verification.json).

Для #12 остаются HTTP-проверки нового сервиса: отказ без токена/при чужом source,
изолированные одноимённые таблицы двух подключений, неверный JSON/числа/типы,
несовместимая схема, отсутствие артефакта без fit, межполевые ограничения,
совпадение ответа с выбранной моделью и сохранение версии в дашборде.
