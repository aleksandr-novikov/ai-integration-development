Протокол фиксируется в Git до пяти зачётных запусков. Данные — стандартный набор #7; перед экспериментами обязательна успешная валидация #8. Никаких изменений данных, разметки или признаков по результатам test.

Baseline повторяет рецепт `ml/anomaly_detector.py`: StandardScaler, IsolationForest, seed=42, score=decision_function, сигнал при score < 0. `max_samples=256` эквивалентен исходному `auto` при 1343 обучающих наблюдениях на таблицу. Меняется один фактор относительно baseline; взаимодействия факторов и несколько seed в эту серию не входят. Порог определяется contamination на train, дополнительной калибровки по test нет.

Используем четыре признака из #7: row_count, null_rate, d_row_count, d_null_rate. На каждой таблице отдельно обучаем scaler и модель исключительно на train; переиспользуем `fit_training_scaler` и `load_features`. Текущий промышленный `train()` загружает 60 дней из БД, поэтому не вызывается: это нарушило бы фиксированное разбиение учебного набора. Алгоритм и baseline сохраняются; эксплуатационный код не меняется.

## Метрики

Precision, recall, F1 рассчитываются по отдельным наблюдениям: положительный класс — `is_anomaly=1`, TP/FP/FN/TN суммируются по всем таблицам (micro). При нулевом знаменателе precision/recall/F1 записывается 0. FPR = FP/(FP+TN) только по нормальным наблюдениям; при их отсутствии значение null, а не 0.

События сопоставляются по `(project_id, table_name)` и включённым границам `[start,end]`, как в CASE.md. Хотя бы один сигнал внутри интервала означает обнаружение события. Event recall = найденные события / все события; повторные сигналы внутри одного события не увеличивают число найденных. Задержка — число шагов от start до первого сигнала. Медиана рассчитывается только среди обнаруженных событий; пропуски явно представлены в event_recall и таблице событий. Отдельно считаем медиану для резких событий null_spike/volume_jump, к которым относится критерий задержки CASE.md. При отсутствии событий/обнаружений соответствующие показатели null и критерий не выполнен. Все метрики представлены долями, задержка — в тиках по 15 минут.

## Выбор до test

Цели CASE.md: event recall ≥ 0.8, FPR ≤ 0.1, медиана задержки резких событий ≤ 1 тик. Среди удовлетворяющих всем целям на validation выбираем максимальный point F1, затем меньший FPR, меньшее число деревьев и имя конфигурации для разрешения равенства.

Если ни один кандидат не соответствует целям, выбираем минимальный FPR, затем максимальный event recall, затем point F1, затем имя. Это диагностический победитель; достижение целей не утверждается. Правило ориентировано на ограничение ложных тревог и фиксируется до результатов.

После выбора записываем selection.json. Только затем вычисляем предсказания на test для выбранных трёх моделей, без переобучения на train+validation, отдельным шестым run `final_test`. Прочие кандидаты на test не оцениваются. Валидатор читает test только для проверки структуры и согласованности, не для выбора модели.

## Воспроизводимость и интерпретация

Во всех runs сохраняем параметры, seed, dataset_id, SHA-256 файлов, Git SHA, хеши исходников, версии Python/библиотек, метрики, предсказания, таблицу событий, scaler+модель каждой таблицы. MLflow хранится локально в SQLite; экспорт с JSON и артефактами можно импортировать на другом компьютере без чужого сервера.

Влияние параметра оцениваем по разности метрик validation относительно baseline, основной показатель — абсолютное изменение point F1; изменения FPR и event recall приводим рядом. Это локальное сравнение выбранных значений на одном seed, не доказательство глобальной важности параметра. В test девять событий; выводы ограничены синтетическим набором. Следующие исследования используют новую заранее объявленную серию и отдельный закрытый тест, а не повторную настройку по уже раскрытому test.
